much as the models: where a model runs, how code calls it, and the LLM tools engineers develop
with. It stays provider- and framework-agnostic, and every demo also runs on a local model
(Ollama or LM Studio), in the browser, or with the offline stand-in the drafts already use, so
no student is blocked by credits.

## Module learning objectives
- Explain in plain terms what an LLM does: text becomes tokens, the model gives a probability
  for the next token, one is sampled, and the loop repeats; and why that explains fluency,
  hallucination, cost and the context limit.
- Count the tokens in a request and estimate what it costs.
- Call an LLM with system and user messages, a temperature and a token limit, through a hosted
  API or a local model, and get output that validates against a schema.
- Run an open-weight model locally with Ollama or LM Studio, and call it with the same code as a
  hosted API.
- Use embeddings to measure how similar two pieces of engineering text are.
- Decide what goes into the context window and how it gets there: tools, keyword search,
  semantic search and reranking, and measure each choice on a gold set of queries.
- Recognize the failure modes that matter in engineering work: invented numbers, units and
  citations, confident wrong answers, and answers built on the wrong context.

## Lecture L17 — Large language models: what they are and how to use one
**Objectives:**
- Describe an LLM as next-token prediction and connect it to the transformer from L12.
- Explain tokens and the context window, and how tokens set cost and latency.
- Make a first call to an LLM and read the token usage it reports.
- Use embeddings and cosine similarity to find similar engineering text.
- Write a clear prompt with instructions, examples, the text to work from and permission to
  answer "not found", and get output that validates against a schema.

**Topics:**
- From L12's transformer to an LLM: pretraining to predict the next token on a large amount of
  text, then instruction tuning, which is why a chat model follows instructions (one slide).
  The generation loop; temperature and sampling.
- Tokens: what they are and how to count them; why "±0.05 mm", "AISI 4140" and part numbers
  split into surprising pieces; the context window as a budget; price per token.
- Using one: system, user and assistant messages; temperature and the token limit; the usage
  fields in the response; the API key in an environment variable, never in the code.
- **Where the model runs**, as a toolchain decision:
  - a hosted API (largest models, pay per token, data leaves the machine);
  - **Ollama**: a command-line tool and local server for open-weight models, with an
    OpenAI-compatible API at `http://localhost:11434/v1`, made for scripts and servers;
  - **LM Studio**: a desktop app to find, download and chat with models, which also serves an
    OpenAI-compatible API at `http://localhost:1234/v1`;
  - the same client code reaches all three by changing `base_url`, which is the systems lesson;
  - both local tools run quantized GGUF models: an 8-billion-parameter model at 4 bits needs
    roughly 5 GB of memory, and proprietary engineering documents never leave the laptop.
- Embeddings: text becomes a vector, and cosine similarity compares two texts; finding
  near-duplicate maintenance-log entries ("bearing noise", "noisy bearing", "brg vibration").
  L18 builds search on this.
- What LLMs are good and bad at in engineering work: drafting, summarizing, extracting and
  coding help, against arithmetic, unit conversion, citing sources and recent facts.
  Hallucination follows from next-token prediction; it is not a bug that will be fixed.
- **Prompting** (moved from the old L18): system instructions, zero-shot and few-shot,
  grounding in provided text, asking for "not found" instead of a guess, and temperature 0 for
  extraction.
- **Structured output** (moved from the old L18): a schema-enforced JSON mode and a Pydantic
  model to validate the result; a failed validation is a retry, not a crash. A small labeled set
  of 10 to 30 examples, so two prompts are compared on numbers instead of by eye.

**Live demo / in-class activity:** Tokenize a line of an equipment datasheet and count the cost
of a 40-page manual. Send the same question at temperature 0 and at 1, and read the usage
fields. Run the same script against a hosted model and against a local model in Ollama (or LM
Studio), changing only `base_url`, and compare speed, cost and answer. Embed 30
maintenance-log entries and cluster the near-duplicates; students predict the clusters first.
Then a structured extractor over component datasheets (moved from the old L18): a Pydantic
schema, validation, and a datasheet without a pressure that shows the "null, do not invent"
behavior.

**Engineering framing / dataset:** Equipment datasheets and free-text maintenance logs: units,
part numbers and abbreviations are where LLMs and tokenizers stumble.

**Readings & resources:**
- 3Blue1Brown, "Large Language Models explained briefly" (video, 2024).
- Karpathy, "Intro to Large Language Models" (talk, 2023).
- Alammar, "The Illustrated Transformer": a refresher on L12.
- Your provider's pages on tokens, models and pricing (read the current version).
- Ollama documentation, including its OpenAI compatibility page; LM Studio documentation, its
  OpenAI-compatible server.
- Your provider's guides to prompting and structured output; Pydantic documentation.

## Lecture L18 — Context engineering: tools, search and retrieval
**Changed 2026-10-11:** replaces "Reliable LLM outputs" (prompting and structured output moved
to L17) and absorbs the RAG lecture. Planned for 90 minutes, with the notebook and questions in
the remaining 20.

**Objectives:**
- Explain context engineering: an LLM answers from what is in its context window, so deciding
  what goes there, and how it gets there, determines the answer.
- Give a model a tool, explain the tool-call exchange, and recognize when fetching context on
  demand (reading files, searching the web) is the right design, and the prompt-injection risk
  it brings.
- Build keyword search with an inverted index and BM25, and explain what it finds and misses.
- Build semantic search with embeddings, combine it with keyword search, and rerank the result
  with a cross-encoder; explain where late interaction (ColBERT) sits between them.
- Assemble a grounded prompt with citations within a token budget, and measure retrieval with
  recall@k and MRR on a gold set of queries.
- Trace each stage of a retrieval pipeline running in the browser: what runs at build time,
  what runs on the page, and what each costs.

**Topics** (minutes are a budget for the 90-minute lecture):
- **Why this matters** (5 min). The model answers from its context window and nothing else at
  inference time (L17's budget). Context engineering is choosing what goes in. A correct-sounding
  answer built on the wrong passage is the failure to open on.
- **Fetching context with tools** (10 min). One tool call, message by message: a JSON schema
  in, a tool request out, your code runs it, the result goes back. Read, glob and grep over files
  (how coding agents search a repository without an index), web search and fetch (fresh, but
  untrusted). The Model Context Protocol as the standard plug for tools and resources. Indirect
  prompt injection: a fetched page that carries an instruction aimed at the model. Multi-step
  loops are named and left for L19.
- **Keyword search over a document store** (13 min). The inverted index; TF-IDF and then BM25
  written out, with what k1 (term saturation) and b (length normalization) do. SQLite FTS5 over
  the notes, back to L3–L4. Strong on exact identifiers (`zero_grad`, Parquet, nDCG); weak on
  paraphrase, synonyms and vocabulary mismatch.
- **Semantic search** (16 min). Chunking the notes by section, keeping source, section and
  slide. A bi-encoder embeds each chunk once (L17's sentence embeddings); a query is embedded and
  compared by cosine. Exact search with NumPy, then approximate nearest neighbors (HNSW) in one
  diagram, with FAISS, sqlite-vec and pgvector as the places it lives. Hybrid search with
  reciprocal rank fusion, because the two retrievers fail on different queries.
- **Reranking and late interaction** (13 min). A cross-encoder reads the query and a passage
  together and scores the pair: more accurate, too slow to run over a corpus, so it reranks the
  top 20 to 50. ColBERT keeps one vector per token and scores with MaxSim, between the bi-encoder
  and the cross-encoder in cost and quality; the storage it needs.
- **Tuning and scaling** (8 min, added 2026-10-11). The knobs and what they cost, each tied to a
  number from the notebook rather than a rule of thumb:
  - chunk size and overlap: small chunks retrieve precisely and lose context, large ones dilute
    the topic and overrun the embedding model's input limit (all-MiniLM-L6-v2 truncates at 256
    word pieces); overlap of a sentence or two keeps an idea that spans a boundary; section
    boundaries first, then a size cap. The notebook sweeps size and overlap against recall@5.
  - choosing the embedding model: start from a public leaderboard (MTEB), then decide on your
    own gold set; dimension, maximum input length, domain, license, and local against an API
    (an API sends every document to the provider). Re-embedding the corpus is the cost of
    switching, so pin and version the model with the index.
  - memory and disk: N × d × bytes per number. One million 768-dimension chunks is about 3 GB in
    float32, 0.8 GB in int8 and about 0.1 GB in binary; an HNSW graph adds its links; ColBERT
    stores one vector per token, which is why its compression matters.
  - search time: exact search costs N × d multiply-adds per query, milliseconds for this corpus
    and still fast for a few hundred thousand chunks; past that, approximate search (HNSW) trades
    a little recall for speed through its search-breadth setting, and the trade is measured
    against exact search on the same queries.
  - at larger scale, the index moves to a server: Postgres with pgvector (keeps SQL, roles,
    backups and the L3–L4 database), OpenSearch or Elasticsearch (BM25 and vector search in one
    engine), or a dedicated vector database (Qdrant, Weaviate, Milvus; Pinecone as a managed
    service); in-process options (FAISS, sqlite-vec, LanceDB, Chroma) until then. What changes
    on a server: authentication (API keys or database roles, TLS, secrets out of the code as in
    L1–L2), permissions per document enforced as a metadata filter at query time so a user never
    retrieves what they cannot read, incremental updates and deletes, and backups. Product
    details to be verified before they enter the notes.
- **Assembling and measuring the context** (10 min). Packing the prompt within a token budget,
  ordering (lost in the middle), citations, and "not in the notes". The recall ladder: recall@5
  and MRR for BM25, dense, hybrid, reranked and ColBERT on the same gold set.
- **Capstone: chat with the course notes** (10 min). The deck answers questions about the
  released notes, entirely in the browser. At build time: chunk the released notes, compute
  embeddings, write an index file. On the page: BM25 (MiniSearch) and embedding search
  (transformers.js, the same model) fused by RRF, an optional cross-encoder reranker, prompt
  assembly with citations shown to the student, and generation by WebLLM on the GPU through
  WebGPU, loaded only on request. Without WebGPU it falls back to showing the retrieved passages
  and their links. Each block is shown with where it runs and what it costs.
- **Limitations and trade-offs** (5 min). A one-billion-parameter model in a browser tab
  summarizes and quotes; it does not reason well. Freshness, prompt injection, cost of tokens,
  and when to skip retrieval: a small, stable corpus fits in the context window. The choice
  between a better prompt, retrieval and fine-tuning as one table (from the old RAG lecture).

**Live demo / in-class activity:** `l18-context-engineering.ipynb`, CPU only, no API key: chunk
the released course notes, build BM25 (SQLite FTS5 and a short hand-written version), dense and
hybrid retrieval, a cross-encoder reranker and a small ColBERT model, and print the recall ladder
on the gold set, including queries each stage wins and loses. A short tuning section sweeps
chunk size and overlap against recall@5, and times exact search against an HNSW index (FAISS) on
a synthetic set of a few hundred thousand vectors, with memory reported for each. Then the
capstone in the deck:
ask it a question about an earlier lecture and read the prompt it assembled.

**Engineering framing / dataset:** The course's own released notes (L1 to L17 at release), a
technical corpus with exact identifiers, equations, units and paraphrase, and the one corpus
every student has read part of. About 20 gold queries with the section that answers each,
chosen so each stage has queries it wins: exact identifiers (keyword), paraphrase (dense),
near-duplicate sections (reranking), and questions the notes do not answer ("not in the
notes"). Only notes listed in `_toc.yml` are indexed, so instructor-only material and
unreleased lectures stay out by construction.

## Teaching notes / common pitfalls
- Keep the architecture at the level of intuition. L12 already taught attention; the goal here
  is a correct mental model of next-token prediction, not the math.
- Students conflate "the model returned JSON" with "the JSON is correct". Validation and a
  small labeled set from day one; this is the habit the whole arc depends on.
- Units and numbers are where extraction fails quietly: "2.5" as a string, MPa against bar.
  Put units in the schema.
- Silent truncation: someone will paste a 60-page PDF into one call. Make counting tokens a
  required step.
- Non-determinism confuses debugging; use temperature 0 for extraction and pin the model ID.
- Access: make sure every demo and assignment has a path without paid credits (a local model
  or the offline stand-in), and say which one a student used in their report.
- Local models need memory. Name a model size that fits the course laptops, LM Studio for
  exploring and Ollama for scripts, and a fallback for students whose machines cannot run one.
- L18: students judge retrieval by reading answers. Require the recall ladder on the gold set
  before any claim; a good answer over a bad retrieval is luck.
- L18: pin the embedding model. Embedding queries with a different model than the index
  silently ruins retrieval; the capstone uses the same model at build time and in the browser
  for this reason.
- L18 tuning: students want a best chunk size. There is none; there is a sweep on a gold set.
  Keep the section short and quantitative, one slide per knob.
- L18 scaling: permissions are the part engineers forget. A shared index without a per-document
  filter leaks every document to every user who can ask a question.
- L18: keep the vector-database zoo to one table. The ideas are the index and the distance;
  the products change every year.
- L18: ColBERT is easy to name-drop. Show the MaxSim matrix for one query and one passage.
- L18 capstone: the model download is a few hundred MB to about 1 GB. Load it before class on
  the projector machine, and expect some laptops to have no WebGPU; the retrieval-only fallback
  is the part worth inspecting anyway.
- L18 capstone: it breaks the widgets' "no network access" rule on purpose (model weights and
  libraries are fetched on request). Say so, and say why the rule exists.
