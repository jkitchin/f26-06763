The course is deliberately **provider- and framework-agnostic**: you will call a *hosted* LLM API (e.g. Anthropic or OpenAI), and the concepts (tokenization, embeddings, context budget, structured output, prompt design) transfer across providers. Pick one provider for your assignment; do not hard-code assumptions that only hold for one.

## Module learning objectives
- Explain, at a systems level, what a transformer-based LLM does: tokenization → embeddings → attention → next-token distribution, and why this makes context length, latency, and cost the primary engineering constraints.
- Tokenize real engineering text and quantify how tokenization affects cost, truncation, and numeric/units handling.
- Use embeddings to represent engineering text and compute similarity; distinguish token embeddings from sentence/document embeddings.
- Call a hosted LLM API reliably: manage the message/prompt interface, `max_tokens`, temperature/latency trade-offs, retries, and cost accounting.
- Produce **schema-constrained structured output** from unstructured engineering text and validate it programmatically.
- Design and iterate prompts methodically (zero/few-shot, role/system instructions, grounding) and evaluate them instead of eyeballing.

## Lecture L15 — LLM architecture intuition, tokenization, embeddings
**Objectives:**
- Build a correct-enough mental model of a decoder-only LLM to reason about failure modes (truncation, hallucination, context limits) rather than treat it as a black box.
- Understand tokenization concretely: subword units, why "10.5 MPa" or "SS316L" may split oddly, and how token counts drive cost/latency.
- Understand embeddings as vectors and use cosine similarity to cluster/retrieve engineering text.

**Topics:**
- Decoder-only transformer at a block-diagram level: input tokens → embedding lookup + positional info → stacked attention/MLP blocks → logits → next-token distribution → sampling. Autoregressive generation loop.
- Why "it predicts the next token" explains both fluency and hallucination; temperature/top-p as sampling knobs.
- Context window as a hard budget (tokens in + tokens out); what happens at the limit (error or silent truncation depending on provider).
- Tokenization: byte-pair/subword encoding; whitespace and casing sensitivity; multi-token numbers, units, chemical formulas, and code identifiers. Use the provider's token-counting endpoint/library — never estimate with a foreign tokenizer (e.g. an OpenAI tokenizer for an Anthropic model, or vice versa).
- Embeddings: token vs pooled sentence/document embeddings; embedding model APIs; cosine similarity; dimensionality; when embeddings are a better tool than an LLM call (dedup, clustering, nearest-neighbor retrieval — the bridge to Wk10 RAG).

**Live demo / in-class activity:** Take a page of a real datasheet or standard (e.g. a pump datasheet or an ASTM-style materials spec). (1) Tokenize it with the provider's tokenizer and count tokens; show that "±0.05 mm", "Ø25", and "AISI 4140" fragment into surprising token counts and that a 40-page PDF blows past a naive context budget. (2) Embed ~30 short maintenance-log entries, compute a cosine-similarity matrix, and cluster near-duplicate failure descriptions ("bearing noise" vs "noisy bearing" vs "brg vibration"). Students predict which pairs cluster before we compute.

**Engineering framing / dataset:** Equipment datasheets / material specifications (units-heavy, tabular-in-prose) and free-text maintenance/inspection logs. These expose tokenization pain (units, part numbers) and motivate embeddings for messy real-world engineering text.

**Readings & resources:**
- Vaswani et al., "Attention Is All You Need" (2017) — skim for the architecture diagram, not the math.
- Jay Alammar, "The Illustrated Transformer" and "The Illustrated Word2vec" — visual intuition.
- Your chosen provider's docs: *tokenization / token counting*, *embeddings*, and *models/pricing* pages (read the current version — pricing and context limits change).
- Bommasani et al., "On the Opportunities and Risks of Foundation Models" (2021) — read the intro/framing for the "systems" view.

## Lecture L16 — The API/prompt/structured-output interface; context, cost, latency; prompting
**Objectives:**
- Call a hosted LLM API robustly and account for cost and latency as first-class engineering metrics.
- Get **validated, schema-constrained** output out of an LLM and handle the cases where it fails.
- Apply a disciplined prompting method and *measure* prompt quality on a small labeled set.

**Topics:**
- The request/response interface common across providers: system vs user messages, `max_tokens`, temperature, stop conditions, streaming vs non-streaming, and reading token-usage fields from the response.
- Structured output two ways: (a) **schema-enforced JSON** (provider "structured output"/JSON-schema modes, e.g. `output_config.format` / `response_format` / equivalent) and (b) **tool/function-calling** with a typed argument schema. Validate the result with a Pydantic model or JSON Schema; treat validation failure as a retry/repair loop, not a crash.
- Context/cost/latency management: prompt caching for a large fixed context, batching, choosing a smaller/faster model for easy subtasks, and setting a sane `max_tokens`. Track cost per call and per document.
- Prompting technique: clear role/system instructions; zero-shot vs few-shot; grounding the model in provided text and instructing it to say "not found" instead of inventing; asking for citations/spans; determinism (low temperature) for extraction tasks.
- Reliability engineering: retries with backoff on rate limits/5xx, idempotency, logging prompts + responses + usage (reuse MLflow or simple structured logs from Wk5), and never silently truncating inputs.
- Prompt *evaluation*: build a tiny gold set (10–30 examples) with known correct extractions and score exact/field-level accuracy so prompt changes are measured, not guessed.

**Live demo / in-class activity:** Live-build a structured extractor over a datasheet: define a Pydantic schema (e.g. `Component(part_number, material, max_pressure_MPa, operating_temp_range_C, mass_kg)`), send the datasheet text with a schema-constrained request, parse and validate, and print token usage + estimated cost. Then deliberately break it (a datasheet missing pressure) to show the "field not present → null, don't hallucinate" behavior and the validation/repair loop. Compare a naive prompt vs an improved one against a 10-example gold set and show the accuracy delta and cost delta side by side.

**Engineering framing / dataset:** A small set of heterogeneous component datasheets (valves, pumps, fasteners, or electronic parts) plus a handful of intentionally-incomplete ones. Output feeds a normalized parts table — exactly the kind of ingestion task an AI engineer automates.

**Readings & resources:**
- Your provider's *structured outputs / JSON mode* and *tool (function) calling* guides (current version).
- Your provider's *prompt engineering* guide; plus the OpenAI or Anthropic prompting best-practices page for the cross-provider view.
- Pydantic docs — models and validation.
- Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (2023) — why stuffing everything into context is not free.

## Teaching notes / common pitfalls
- Students conflate "the model returned JSON" with "the JSON is correct/valid." Force a validation step and a small gold set from day one — this is the habit the whole arc depends on.
- Watch for silent truncation: someone will paste a 60-page PDF into one call, hit the context limit, and not notice. Make token counting a required step.
- Units and numeric parsing are where extraction quietly fails ("2.5" as string vs float, MPa vs bar vs psi). Require explicit units in the schema and a normalization step.
- Cost blindness: without logging token usage, students can't reason about the systems trade-offs. Require per-call usage logging in A8.
- Non-determinism confuses debugging. Use low temperature for extraction and fix seeds where the provider supports it; teach that "it worked once" is not a passing test.
- Provider drift: model IDs, context limits, and pricing change. Tell students to read the *current* docs and pin the model ID they used in their report.
