This week answers the central practitioner question: **when the base model doesn't know your engineering domain, what do you do?** Three levers — better prompting, retrieval (RAG), and fine-tuning (LoRA/PEFT) — with a clear decision framework for choosing among them. Still provider-agnostic for the hosted LLM; fine-tuning uses small **local open models** on the course GPU.

## Module learning objectives
- Build a working RAG pipeline over an engineering corpus: chunk → embed → index → retrieve → ground → generate.
- Choose chunking and retrieval parameters deliberately and justify them with retrieval-quality metrics, not vibes.
- Measure retrieval quality (recall@k, precision@k, MRR/nDCG) and end-to-end answer quality (grounded/faithful, correct, cites sources).
- Compare prompting vs RAG vs fine-tuning on cost, latency, freshness, and failure modes, and pick the right tool for a given engineering task.
- Fine-tune a small open model with LoRA/PEFT on the GPU and evaluate whether it actually helped versus a RAG or prompting baseline.
- Recognize and mitigate RAG failure modes: retrieval miss, context dilution, stale index, and confidently-wrong grounding.

## Lecture L17 — Retrieval-augmented generation & vector databases
**Objectives:**
- Explain why RAG exists (grounding, freshness, source attribution, cost vs long-context) and where it breaks.
- Build each stage of a RAG pipeline and reason about the design choices at each stage.
- Evaluate retrieval quality quantitatively and connect retrieval failures to downstream answer failures.

**Topics:**
- RAG anatomy: ingestion (load → clean → **chunk** → embed → index) and query (embed query → retrieve top-k → assemble grounded prompt → generate with citations).
- Chunking strategy: fixed-size vs structure-aware (by section/heading/table), chunk size and overlap trade-offs, and why engineering docs (specs with clauses, tables, figure captions) resist naive fixed-size chunking. Metadata to keep (source, section, page, revision).
- Vector databases and indexes: what a vector DB provides (ANN search, metadata filtering, persistence). Name options — FAISS (in-process), Chroma, Qdrant, pgvector (Postgres, connects back to Wk2) — and pick by scale/ops needs, not hype. Exact vs approximate nearest neighbor; the recall/latency trade-off.
- Retrieval mechanics: dense (embedding) retrieval, keyword/BM25, and hybrid; metadata filters (e.g. restrict to the current spec revision); re-ranking with a cross-encoder.
- Grounding the generation: instruct the model to answer *only* from retrieved context, cite chunk IDs/sources, and say "not in the provided documents" otherwise. Handling conflicting or duplicate chunks.
- **Retrieval evaluation:** build a small query→relevant-chunk gold set; compute recall@k, precision@k, MRR, nDCG. Separate *retrieval* metrics from *answer* metrics (faithfulness/groundedness, correctness, citation validity). Introduce LLM-as-judge as one tool (with its caveats — deferred fully to Wk12).

**Live demo / in-class activity:** Build a minimal RAG loop end to end over an engineering standards/manual corpus: chunk by section, embed, index in FAISS or Chroma, retrieve top-k for a query like "what is the minimum bend radius for 12 mm copper tube?", and generate a grounded, cited answer. Then sweep chunk size (256 vs 1024 tokens) and k (3 vs 8) and show recall@k moving on a 15-query gold set — including a query the retriever *misses* and the resulting confidently-wrong answer, to make the retrieval→answer failure chain concrete.

**Engineering framing / dataset:** A corpus of engineering standards excerpts, equipment O&M manuals, or design handbooks (chunkable technical prose with tables and clause numbers). Queries are the kind of lookups an engineer actually runs. Emphasize source attribution — an ungrounded answer to a code-compliance question is worse than no answer.

**Readings & resources:**
- Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (2020) — the original RAG paper.
- Your vector DB of choice: getting-started docs (FAISS wiki, Chroma, Qdrant, or pgvector).
- Your LLM provider's embeddings + prompt-caching docs (large fixed context is a cost lever).
- Es et al., "RAGAS: Automated Evaluation of Retrieval Augmented Generation" (2023) — a vocabulary for RAG metrics (faithfulness, answer/context relevance).
- Karpukhin et al., "Dense Passage Retrieval for Open-Domain Question Answering" (2020) — dense retrieval fundamentals.

## Lecture L18 — Prompting vs RAG vs fine-tuning; LoRA/PEFT hands-on
**Objectives:**
- Give a defensible answer to "should I prompt, retrieve, or fine-tune?" for a concrete engineering task.
- Understand what LoRA/PEFT does and why it makes adaptation feasible on modest hardware.
- Run a real LoRA fine-tune on a small open model and evaluate it against a baseline.

**Topics:**
- Decision framework across three axes of need — *knowledge* (facts the model lacks), *behavior/format* (style, structured output, domain conventions), and *freshness* (changing data):
  - **Prompting/few-shot:** cheapest, fastest to iterate; limited by context and the base model's latent knowledge.
  - **RAG:** best for large, changing, or proprietary knowledge that must be *cited*; adds retrieval infra and latency.
  - **Fine-tuning:** best for teaching consistent *behavior/format/style* or specialized tasks; poor for fast-changing facts; needs labeled data and eval. These combine — RAG + a lightly fine-tuned formatter is common.
- Full fine-tuning vs parameter-efficient fine-tuning (PEFT). **LoRA:** freeze base weights, train small low-rank adapter matrices; drastically fewer trainable params, small checkpoints, feasible on one GPU. QLoRA (quantized base) for even tighter memory. Key knobs: rank `r`, `alpha`, target modules, learning rate, epochs; overfitting risk on small data.
- Data for fine-tuning: instruction/response pairs, formatting your engineering task as supervised examples, train/val split discipline (no leakage — callback to Wk4/Wk5), and how much data is "enough."
- Serving/evaluating an adapter: load base + adapter, run inference, and — critically — evaluate on a held-out set against the prompting and RAG baselines on the *same* metric.
- Cost/latency/ops comparison: hosted API calls vs self-hosted fine-tuned model; when fine-tuning a small local model actually beats calling a large hosted one.

**Live demo / in-class activity:** LoRA-fine-tune a small open model (e.g. a ~1–3B instruct model via Hugging Face `transformers` + `peft`/`trl` on the course GPU) to produce a domain-specific structured output — e.g. normalizing free-text maintenance logs into a fixed schema, or classifying failure modes — using a few hundred labeled examples. Show trainable-parameter count (<1% of base), the training loss curve in MLflow, and a before/after eval on a held-out set. Then compare against a few-shot prompt baseline and discuss which won and why.

**Engineering framing / dataset:** A labeled engineering text task where *behavior/format consistency* matters — failure-mode classification of maintenance logs, or extraction into a rigid schema — so students see fine-tuning's real strength (consistent structured behavior) rather than using it as a knowledge store.

**Readings & resources:**
- Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models" (2021).
- Dettmers et al., "QLoRA: Efficient Finetuning of Quantized LLMs" (2023).
- Hugging Face PEFT and TRL documentation (LoRA config, `SFTTrainer`).
- "RAG vs Fine-tuning" practitioner comparisons — e.g. the RAFT paper (Zhang et al., 2024) for combining the two.

## Teaching notes / common pitfalls
- The #1 mistake is skipping retrieval evaluation and only judging the final answer. Require a query→relevant-chunk gold set and recall@k *before* any answer-quality claims — a good answer over a bad retrieval is luck.
- Chunking is where most RAG quality is won or lost; students default to fixed 500-char chunks and shred tables/clauses. Push structure-aware chunking and metadata retention.
- "Grounded" is not automatic. Without an explicit instruction to answer only from context and cite sources, models happily blend in pretraining knowledge — which is dangerous for code/spec questions. Test with a query whose answer is deliberately *not* in the corpus.
- LoRA runs will OOM or take too long if students pick too large a base model or batch size. Provide a known-good model + config and a GPU-time budget; make QLoRA the fallback.
- Fine-tuning gets misused as a knowledge store ("teach it our specs"). Redirect: knowledge → RAG; behavior/format → fine-tuning. The assignment and demo should make this contrast explicit.
- Evaluation must be apples-to-apples: same held-out set and same metric across prompting/RAG/fine-tuning, or the comparison is meaningless.
- Embedding-model/index mismatch: re-embedding queries with a different model than the index was built with silently tanks retrieval. Pin the embedding model.
