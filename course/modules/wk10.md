## Module learning objectives
- Explain the agent loop: the model chooses a tool, your code runs it, the model reads the
  result and decides what to do next, until it answers or a budget runs out.
- Build a minimal agent with two or three well-described tools, without a framework.
- Bound the loop with a step budget and a cost cap, and recover from a tool error.
- Apply guardrails: read-only tools, human approval before anything that writes or actuates,
  and treating retrieved text and tool output as untrusted.
- Evaluate an agent on a fixed set of tasks: success rate, steps and cost per task.

## Lecture L19 — LLM agents: tools, loops and guardrails
**Objectives:**
- Explain what an LLM agent is, and when a fixed workflow is the better choice.
- Trace the agent loop message by message, and explain why the tokens it reads grow faster than
  the number of calls.
- Write tool definitions a model can use correctly, with errors it can recover from.
- Bound and guard an agent: a step budget, a stuck check, read-only access, and a person's
  approval before any change to a physical system.
- Measure an agent on a fixed set of tasks, and explain why success falls as $p^n$ with the
  number of steps.
- Describe how coding agents map onto the same loop, and how to work with one safely.

**Topics:**
- What an agent is: an LLM in a loop with tools and a goal. The spectrum from a workflow (you
  write the control flow) to an agent (the model chooses), and why the simplest one that works
  is the right one.
- The loop, message by message: tool definitions in, a tool request out, your code runs it, the
  result goes back, repeat or answer.
- Tool design: clear names and descriptions (the model reads them to decide), typed arguments,
  and error messages the model can recover from.
- Bounding the loop: a step budget, a cost cap, timeouts, and stopping a model that repeats a
  failing call. Logging every step.
- Guardrails: read-only database access, human approval before a write or an actuation,
  prompt injection (retrieved documents and tool output are untrusted input), and validating
  outputs against a schema.
- Evaluation: a fixed set of 10 tasks with known outcomes; success rate, steps and cost per
  task, and what went wrong when it failed.
- **Agents you already use: coding agents.** opencode (open source, in the terminal, works with
  any provider including local models through Ollama or LM Studio), and Claude Code, GitHub
  Copilot and Cursor, map onto the same loop: tools to read, search, edit and run commands;
  a project file (`AGENTS.md`, `CLAUDE.md`) as the system prompt; and permission settings
  (opencode's `allow`, `ask` and `deny` per tool) as the human-approval gate. They are the
  development toolchain of an AI engineer, and the course's rules on AI assistance apply to
  them.
- Frameworks and multi-agent systems in one section: what LangGraph, the OpenAI Agents SDK or
  the Claude Agent SDK manage for you, what you give up, and when one agent coordinating
  specialists is worth its cost (rarely, at first).

**Live demo / in-class activity:** As written, no live demo in class. The deck replays a
scripted agent run on the A -> B -> C tank of L15 (`agent-trace` widget: messages and the input
tokens of each call) and a p^n slider. The worked example, `l19-agents.ipynb`, builds the agent
by hand with four tools (a read-only DuckDB query of last week's log, the L15 yield model with its

model, the four ways a run ends (done, out of budget, stuck, refused after a planted logbook
note), and ten fixed tasks measured against p^n and pass^k. Three clicker questions: tool
units, the lethal trifecta, and p^n.

**Engineering framing / dataset:** Sensor time series in a queryable store, plus a trained
surrogate as a callable tool: an agent that reasons about a physical system and cannot change it
without a person's approval.

## Teaching notes / common pitfalls
- Students reach for a multi-agent framework first. A hand-built single-agent loop first; most
  tasks need nothing more, and a framework is hard to debug without understanding the loop.
- Unbounded loops burn money. Every agent needs a step budget and a cost cap.
- Tool descriptions are prompts. Wrong-tool and wrong-argument errors are usually a vague
  description, not a weak model.
- Guardrails are not polish. The human-approval gate, read-only data access and one
  prompt-injection test are required, because the agent sits near physical and costly systems.
- One lucky run is not evidence; report a success rate on a fixed task suite.
- Coding agents: students will use them for every assignment. Show the permission settings and
  insist on reviewing every diff; an agent given `allow` on the shell can do anything the
  student can.
- Remind students the final-project proposal is due this week.
