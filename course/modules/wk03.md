# Week 03 — Pipelines & Processing
**Arc:** Data Systems · **Lectures:** L5–L6

**Prerequisites (from prior weeks):** Reproducible `uv` project and MLflow basics (Wk1); ability to load data from PostgreSQL/Parquet/DuckDB (Wk2). Comfort writing Python functions and running scripts.

## Module learning objectives
- Build a batch data pipeline as a sequence of pure, testable transform steps with clear inputs/outputs.
- Compare pandas and Polars idioms and explain when lazy/columnar execution matters.
- Explain streaming vs. batch for sensor data and the core streaming concepts (windows, watermarks, late data).
- Encode data-quality expectations as executable checks with pandera and/or Great Expectations, and fail a pipeline on violation.

## Lecture L5 — Dataframes and batch pipelines
**Objectives:**
- Get more familiar with pandas and, most importantly, write Polars code that operates on whole columns at once instead of row by row, including grouping and joining.
- Break a data pipeline into small steps that each read one file and write one file, so a run that fails halfway through can be started again without corrupting anything.
- Explain the difference between pandas running code immediately and Polars planning a computation before running it, and use that difference to choose between the two for a given task.

Note: distributed processing (Dask/Spark) was cut from L5 to make room for the demo; the module objective on scaling out was dropped with it.

**Topics:**
- Dataframe fundamentals: vectorization, `groupby`/aggregate, joins for sensor data; avoiding row-wise Python loops. (Long/wide reshaping was cut: the demo never performs it, so the notes no longer teach it.)
- Polars: lazy vs. eager, expressions, query optimization; why columnar + multithreaded execution is fast; interop with Arrow/Parquet.
- Batch pipeline design: extract → clean → transform → load stages, idempotency, deterministic outputs, caching intermediate Parquet.

**Live demo / in-class activity:** Take the Tennessee Eastman process data and build a 4-stage pipeline (load → drop constant/high-missing columns → impute → aggregate by fault) written twice, once in pandas eager and once in Polars lazy, and benchmark. The data is clean, so a clearly labeled cell injects sensor dropout and a stuck channel to give the cleaning stages real work.

**Engineering framing / dataset:** Tennessee Eastman process (Rieth et al. 2017, Harvard Dataverse, CC0). A simulated chemical plant (reactor, condenser, vapor-liquid separator, recycle compressor, product stripper) logging 52 process variables every 3 minutes, fault-free operation plus 20 fault types. Clean by construction, so the demo injects the dirt for the cleaning stages.

**Readings & resources:**
- Polars User Guide, "Concepts: Lazy API" and "Expressions."
- pandas documentation, "Group by."
- Apache Arrow, "Overview" (in-memory columnar, versus Parquet on disk).
- Tennessee Eastman data (Rieth et al. 2017, Harvard Dataverse, CC0); Downs & Vogel (1993) for the process and its faults.

## Lecture L6 — Streaming concepts and data validation
**Objectives:**
- Distinguish batch from streaming and identify when sensor systems require streaming.
- Explain windowing, event vs. processing time, watermarks, and late/out-of-order data.
- Author executable data-quality checks and integrate them as a pipeline gate.

**Topics:**
- Streaming for sensor/IoT data: bounded vs. unbounded data, at-least-once vs. exactly-once, backpressure; the log abstraction (Kafka/MQTT) at a concepts level.
- Windowing: tumbling/sliding/session windows; event-time vs. processing-time; watermarks and handling late-arriving sensor readings.
- Micro-batch as a practical middle ground; why most engineering teams start with scheduled batch.
- Data validation: schema checks (types, ranges, units), statistical expectations (nulls, uniqueness, distributions), physical-plausibility checks (temperature within instrument range, monotonic timestamps).
- Tools: pandera (schema-as-code, integrates with pandas/Polars) and Great Expectations (expectation suites, data docs); where checks live in a pipeline and how failures should behave (block vs. warn vs. quarantine).

**Live demo / in-class activity:** `l06-validation.ipynb`. Collect about three minutes from the live Tennessee Eastman publisher over MQTT, decode the nested OPC UA payloads into one row per reading, and generate a pandera schema from the retained birth message rather than typing the tag list out a second time. Run two gates, one asking whether the publisher kept its contract and one asking whether the data is fit to average. Quarantine the flagged and physically impossible rows with a reason attached, deduplicate on `(tag, sourceTimestamp)` to expose the confident wrong number the held analyser values would otherwise produce, then check each tag's staleness against what the contract predicted, sweep a watermark allowance, and compute the same tumbling average bucketed by event time and by publish time.

**Engineering framing / dataset:** the live Tennessee Eastman stream for the demo, the same feed A3 collects from, so the session is worked on data nobody has cleaned and whose answers nobody knows in advance. The notes and the two figures keep the Intel Berkeley Lab readings from L3 and L4, read in the order they landed rather than sorted, which is what makes out-of-order arrival concrete: 79.5% of the readings arrive after a newer one. The plant feed carries the same problem from a different cause, a publisher that buffers through a network outage and drains the backlog afterwards.

Note: SECOM was planned as this session's validation dataset and dropped. L3 and L4 already use the Intel Lab feed, it carries genuine dirt and genuine late data, and validating a dataset the class already knows costs no time explaining a new one. SECOM is still introduced in L9, where the 6.6% failure rate is the point, so it enters the course there rather than here.

**Readings & resources:**
- pandera documentation, "DataFrameSchema" and "Checks."
- Great Expectations documentation, "Core concepts: Expectations."
- Tyler Akidau et al., "The Dataflow Model" (VLDB 2015) or the "Streaming 101/102" articles — for windowing/watermarks.
- Apache Kafka documentation, "Introduction" (concepts only).

## Assignment
**A3 — A plant stream, collected and made trustworthy** — Students collect at least ten minutes of a live Tennessee Eastman simulation streamed over MQTT from `kitchin-services.cheme.cmu.edu`, then build a pipeline that makes what arrived trustworthy: decode and reshape (Polars, on a `LazyFrame`), validate with pandera and quarantine rather than drop, deduplicate and choose a watermark, reindex onto the regular sample grid and fill the holes with a mask recording which cells they invented, and window over event time to find a disturbance episode. Six points in six groups, five decided by `a03-evidence.py` and the sixth by the TA reading `REPORT.md`. Released L6, due ~1 week later. Full spec: `assignments/a03.md`; the stream itself is `stream/`.

The streaming is in the collection rather than the processing, deliberately: the students land the feed durably and then process the landed file, which is the shape a plant historian actually has and the reason this module's topic list carries micro-batch as the practical middle ground. A genuinely incremental pipeline, replaying the raw file one message at a time against a bounded buffer and reporting what a watermark would have emitted and when, is A3's last stretch item and is ungraded. It is the obvious thing to promote if the mini-project wants a streaming component.

## Teaching notes / common pitfalls
- Students write one giant function. Insist on small pure stages with typed inputs/outputs; it makes testing and caching possible.
- Polars lazy confuses newcomers — nothing runs until `.collect()`. Demo the query plan and the collect step explicitly.
- Do not let students spin up a real Kafka cluster; keep streaming strictly concepts + a laptop demo. The learning objective is judgment, not ops.
- The L6 demo collects live, so it needs the broker up and the room on a network. Check liveness before class with the recipe in `stream/README.md`, and leave a `data/l06-stream.ndjson` from a previous run in `lectures/l06/`: the notebook reuses a capture when one is there and only goes to the network when it is not, so a dead link costs the demo nothing.
- Validation is often treated as decoration. Make them inject bad data and prove the pipeline halts. A check that never fails is untested.
- Leakage sneaks in during "cleaning" (e.g., imputing with global statistics computed over all data). Flag it here; it is the focus of Wk4. Task 5's fill is the hook: a forward fill uses only the past and is safe, a column mean over the whole capture is not, and the two are one keystroke apart.
- Task 5's grid is deliberately the only place the missing data becomes visible. A 30-plant-minute window holds ten samples, so windowing straight off the long table absorbs every hole and the student never meets one. Measured on a 12-minute capture: the per-sample wide table is 20.9% empty with 59 of 603 rows complete, and the 30-minute window table is 61 x 53 with zero holes.
