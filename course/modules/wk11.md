# Week 11 — Agentic engineering
**Arc:** LLM & agentic engineering · **Lectures:** L19–L20

**Prerequisites (from prior weeks):**
- Tool/function-calling and structured output from the LLM API (Wk9, L16) — the mechanism that makes agents possible.
- RAG and retrieval as a callable capability (Wk10) — retrieval becomes one tool among several.
- The Wk7 surrogate model and any Wk5/Wk6 trained model — wrapped as callable tools this week.
- Data access from prior weeks (SQL/DuckDB/Parquet, Wk2–3) — agents query real engineering data.

This week turns single LLM calls into **agents**: systems where the model decides which tools to call, in what order, observes results, and iterates toward a goal. We keep the framework-agnostic stance — you'll understand the raw tool-calling loop first, then see what frameworks add. Emphasis throughout on **evaluation and guardrails**: an unevaluated, unguarded agent is a liability, not a feature.

**Final-project proposals are due this week (Wk11).** The final project itself is specified separately; this module only notes the deadline. Your A10 agent is a strong candidate to grow into a final project.

## Module learning objectives
- Explain the agent loop (plan → call tool → observe → decide → repeat → stop) and implement it against a hosted LLM's tool-calling interface.
- Define safe, well-typed tools that wrap engineering data sources and models (including a surrogate from Wk7), and let an LLM orchestrate them.
- Design stopping conditions, step/cost budgets, and error handling so agents terminate and degrade gracefully.
- Apply guardrails: input/output validation, tool allow-lists, human-in-the-loop approval for consequential actions, and injection-aware handling of retrieved/tool content.
- Evaluate an agent: task success rate, tool-call correctness, steps/cost per task, and failure taxonomy — on a fixed task suite.
- Reason about when to hand-roll an agent loop vs adopt a framework, and about single- vs multi-agent designs.

## Lecture L19 — Agent fundamentals: tool use, function calling, planning/execution loops
**Objectives:**
- Implement a minimal tool-using agent from scratch against the tool-calling API — no framework.
- Design tool schemas that an LLM can use correctly and a harness can execute safely.
- Build in termination, budgets, and error recovery so the loop is bounded and debuggable.

**Topics:**
- What "agent" means here: an LLM in a loop with tools and a goal, choosing actions from observations — distinct from a fixed pipeline. The spectrum from workflow (you code the control flow) to agent (the model chooses); prefer the simplest thing that works.
- The tool-calling loop concretely: send messages + tool definitions → model returns a tool_use/function-call request → your harness executes the tool → return the result → model decides next call or final answer. Repeat until done or budget hit.
- Tool design: clear names, precise descriptions (the model reads these to decide *when* to call), typed JSON-schema arguments, `strict`/validated inputs, and informative error results (return an error the model can recover from, don't crash the loop).
- Planning patterns: single-step tool use, ReAct-style reason+act, and plan-then-execute; when explicit planning helps vs adds latency.
- Bounding the loop: max steps, token/cost budget, timeouts, and detecting/breaking loops where the model repeats a failing call. Logging every step (prompt, tool call, result, usage) for debuggability — reuse MLflow/structured logs from Wk5.
- Determinism and testing: low temperature for tool-selection reliability; unit-testing tools independently of the LLM; recording traces.

**Live demo / in-class activity:** Hand-build (no framework) a tool-using agent over an engineering dataset. Define 2–3 tools — e.g. `query_sensor_db(sql_or_params)` over a Parquet/DuckDB time-series table, `compute_stats(series)`, and `call_surrogate(x)` wrapping the Wk7 surrogate model — and let the agent answer "which operating condition minimizes predicted energy use given last week's sensor ranges?" Walk through the raw request/response messages, show the model choosing tools and observing results, then impose a 6-step budget and demonstrate a graceful stop and a tool-error recovery.

**Engineering framing / dataset:** Sensor/simulation time-series in a queryable store plus a trained surrogate model as a callable. This is the canonical AI-in-engineering agent: it *queries real data* and *calls a model* to reason about a physical system — exactly the A10 task.

**Readings & resources:**
- Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models" (2022).
- Your provider's *tool use / function calling* guide (current version) — message shapes and the loop.
- Anthropic, "Building Effective Agents" (2024) — workflow-vs-agent patterns and "keep it simple."
- Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools" (2023) — background on tool use.

## Lecture L20 — Multi-agent orchestration, frameworks, guardrails; agents over engineering tools/data
**Objectives:**
- Evaluate agent frameworks and decide when to adopt one vs stay with a hand-rolled loop.
- Design multi-agent systems (orchestrator + specialists) and know their costs.
- Implement guardrails and evaluate an agent as an engineering system with a measurable success rate.

**Topics:**
- Frameworks — name options, don't mandate: LangGraph, the OpenAI Agents SDK, Anthropic's Claude Agent SDK, CrewAI, AutoGen, LlamaIndex agents. What they provide (loop management, state, tool registries, tracing, retries, memory) and what you give up (opacity, lock-in, debugging distance). Rule of thumb: start hand-rolled to understand the loop; adopt a framework for orchestration, tracing, and team scale.
- Multi-agent orchestration: orchestrator/coordinator + specialist subagents; when parallel/independent subtasks justify it; handoffs and shared vs isolated context; cost/latency multiplication. Single capable agent first; multi-agent only when the task genuinely fans out.
- Guardrails and safety: input validation and prompt-injection awareness (retrieved documents and tool outputs are untrusted input — never let them silently escalate privileges); output validation against schemas; tool allow-lists and least-privilege (read-only DB creds, sandboxed execution); **human-in-the-loop approval** for consequential/irreversible actions (writes, actuation, spend); rate/step/cost limits.
- Agents over engineering tools/data: wrapping databases, simulators/surrogates, optimization routines, CAD/PLM or ticketing systems, and unit-aware calculators as tools; keeping a human in the loop for anything that touches a physical or costly system.
- **Evaluation:** a fixed task suite with known-good outcomes; metrics = task success rate, tool-call precision/recall (right tool, right args), steps and cost per task, and a failure taxonomy (wrong tool, bad args, hallucinated result, non-termination, guardrail trip). Regression-test the agent as tools/prompts change. (Deeper eval/observability tooling is Wk12.)

**Live demo / in-class activity:** Take L19's hand-rolled agent and (1) re-express it in a framework of choice to show what the framework manages for you and gives you a trace view; (2) add guardrails — a read-only DB tool, output schema validation, a cost cap, and a human-approval gate before any "write/actuate" tool fires; (3) run it against a 10-task suite and report success rate, average steps, and average cost, plus one deliberate prompt-injection attempt in a retrieved document to show the guardrail catching it.

**Engineering framing / dataset:** The same sensor-DB + surrogate setup as L19, extended with a "recommend a setpoint change" tool that requires human approval — making the safety story concrete: the agent can *propose* an actuation but a human must approve it.

**Readings & resources:**
- Documentation for at least one framework you'll consider (LangGraph, OpenAI Agents SDK, or Claude Agent SDK) — read the core loop/orchestration concepts.
- Anthropic, "Building Effective Agents" (2024) — orchestrator-workers and evaluator-optimizer patterns.
- OWASP Top 10 for LLM Applications (current) — prompt injection, excessive agency, insecure tool use.
- Yao et al., "τ-bench: A Benchmark for Tool-Agent-User Interaction" (2024) — how agent success is measured.

## Teaching notes / common pitfalls
- Students reach for a multi-agent framework on day one. Force a hand-rolled single-agent loop first — most tasks need nothing more, and the framework is undebuggable if you don't understand the loop underneath.
- Unbounded loops burn tokens and money. Require a hard step budget and cost cap in every agent; a runaway agent during grading is a real risk.
- Tool descriptions are prompts. Vague descriptions cause wrong-tool/wrong-arg errors that look like "the model is dumb" but are a spec problem. Review students' tool schemas.
- Guardrails are treated as optional polish. Make the human-approval gate and read-only data access *required*, and require one prompt-injection test — the engineering framing (agents near physical/costly systems) makes this non-negotiable.
- Evaluation gets skipped because "it worked in the demo." Require a fixed task suite with success-rate numbers; one lucky run is not evidence.
- Non-termination and flaky tool selection come from high temperature and under-tested tools. Use low temperature, unit-test tools without the LLM, and log full traces.
- Remind students the final-project proposal is due this week and that a well-scoped A10 (or the Wk7 surrogate, or a Wk10 RAG system) is a natural seed for it.
