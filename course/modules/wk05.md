# Week 05 — The ML Workflow, End to End
**Arc:** Machine learning & deep learning · **Lectures:** L9–L10

**Prerequisites (from prior weeks):** A reproducible `uv` project with a lockfile (Wk1);
ability to load and query engineering data from DuckDB/Parquet (Wk2); pandas/Polars
pipelines with schema validation (Wk3); leakage-aware feature engineering, scaling, and
versioned, documented train/validation/test splits (Wk4). You should already be able to
produce a clean, validated feature table with a defensible split.

## Module learning objectives
- Frame an engineering prediction problem as a supervised learning task, choose an
  evaluation metric that matches the engineering cost of error, and establish **strong
  baselines** before reaching for complex models.
- Design and run **cross-validation** correctly for i.i.d., grouped, and time-ordered
  engineering data, avoiding the leakage traps that inflate offline scores.
- Perform an honest **model-selection study**: compare model families and hyperparameters
  on validation data, then report a single held-out test estimate with uncertainty.
- Instrument every training run with **MLflow** — parameters, metrics, artifacts, and the
  exact data/code version — so results are reproducible and comparable.
- Run a systematic **hyperparameter search** (grid, random, and Bayesian/Optuna) and read
  the results without fooling yourself (multiple-comparison and selection bias).

## Lecture L9 — Train, validate, select: baselines, cross-validation, and metrics
**Objectives:**
- Translate an engineering question into a learning task with an appropriate loss and
  reporting metric.
- Build and beat baselines; know when a "sophisticated" model is not actually earning its
  complexity.
- Choose the correct cross-validation scheme for the data's structure.

**Topics:**
- The supervised workflow: problem framing → baseline → model family → validation →
  selection → held-out test → error analysis. Why the test set is touched **once**.
- Baselines that matter in engineering: predict-the-mean / persistence (last value) for
  time series, a linear/ridge model, a single decision tree, and a physics or
  domain-heuristic baseline (e.g., an ideal-gas or empirical correlation). A model that
  cannot beat persistence is not a model.
- Regression metrics and what they mean physically: RMSE (penalizes large errors, same
  units as target), MAE (robust, median-ish), MAPE and its blow-up near zero, R² vs.
  adjusted R², and residual diagnostics. Classification metrics for fault detection:
  precision/recall, PR-AUC vs. ROC-AUC under class imbalance, and the cost matrix of a
  missed fault vs. a false alarm.
- Cross-validation schemes: k-fold and repeated k-fold; **GroupKFold** when rows share a
  unit/specimen/batch (e.g., all cycles from one engine, all cores from one concrete
  batch); **TimeSeriesSplit** / forward-chaining for temporally ordered sensor data.
  Nested CV for unbiased model selection.
- The leakage catalog, revisited from modeling side: fitting the scaler on all data,
  target leakage from future information, group leakage across the split, and
  hyperparameter selection on the test set.
- The bias–variance picture and learning curves: diagnosing underfit vs. overfit by
  plotting train vs. validation error against training-set size and model capacity.

**Live demo / in-class activity:** UCI **Combined Cycle Power Plant** dataset (9,568
hourly records: ambient temperature, exhaust vacuum, ambient pressure, relative humidity →
net electrical power output, MW). Live: build a predict-the-mean baseline, a linear
baseline, and a random forest; compute RMSE/MAE/R²; then deliberately introduce a leakage
bug (scale before split) and show the inflated CV score, then fix it with a scikit-learn
`Pipeline`. Students predict which CV scheme is appropriate and check whether the rows are
truly i.i.d.

**Engineering framing / dataset:** Power-plant output prediction is a canonical
steady-state surrogate problem: cheap-to-measure ambient conditions predict an expensive
performance quantity. The same framing recurs for pump curves, engine maps, and process
yield. Contrast with the **NASA Airfoil Self-Noise** dataset (1,503 rows: frequency,
angle of attack, chord length, free-stream velocity, suction-side displacement thickness →
scaled sound pressure level, dB) to show how feature/target physics changes the metric
choice.

**Readings & resources:**
- Hastie, Tibshirani & Friedman, *The Elements of Statistical Learning*, ch. 7
  (Model Assessment and Selection). Free PDF from the authors.
- scikit-learn User Guide: "Cross-validation: evaluating estimator performance" and
  "Common pitfalls in the interpretation of coefficients / data leakage."
- Raschka, "Model Evaluation, Model Selection, and Algorithm Selection in Machine
  Learning" (arXiv:1811.12808) — the definitive walkthrough of nested CV and reporting.
- UCI Machine Learning Repository dataset pages for Combined Cycle Power Plant and Airfoil
  Self-Noise (dataset documentation and original references: Tüfekci 2014; Brooks,
  Pope & Marcolini 1989).

## Lecture L10 — Experiment tracking with MLflow and hyperparameter search
**Objectives:**
- Instrument a training script so every run is logged, comparable, and reproducible.
- Run grid, random, and Bayesian hyperparameter search and interpret the results honestly.
- Register a selected model with its metrics, params, and data lineage.

**Topics:**
- Why tracking exists: the "which run produced this number?" problem. What to log for every
  run — hyperparameters, git commit SHA, dataset version/hash (tie back to Wk4 data
  versioning), random seed, environment (`uv.lock`), metrics per epoch/fold, and artifacts
  (fitted pipeline, plots, feature importances).
- MLflow concepts: **experiments** vs. **runs**, `mlflow.log_param` / `log_metric` /
  `log_artifact`, autologging for scikit-learn and PyTorch, nested runs for CV folds and
  search trials, the MLflow **Model Registry** and model URIs, and the tracking UI
  (`mlflow ui`). Local file-store vs. a tracking server.
- Hyperparameter search strategy: grid vs. random (Bergstra & Bengio: random beats grid in
  high dimensions) vs. Bayesian/TPE with **Optuna**; search spaces, budgets, pruning of
  bad trials, and multi-fidelity ideas (successive halving / Hyperband). Logging every
  trial to MLflow so the search itself is auditable.
- The statistics of selection: with enough trials some model "wins" by chance. Report the
  validation distribution, use a single held-out test at the very end, and prefer the
  simplest model within one standard error of the best (the 1-SE rule).
- Reproducibility hygiene: seeding, deterministic splits, and re-running a logged run from
  its recorded config.

**Live demo / in-class activity:** Wrap the Week-5 power-plant models in MLflow. Run an
Optuna study over random-forest and gradient-boosting hyperparameters with nested runs,
open `mlflow ui`, sort by validation RMSE, and use the parallel-coordinates and
contour plots to read which hyperparameters mattered. Register the winner and show loading
it back by model URI for a fresh prediction.

**Engineering framing / dataset:** Same power-plant / airfoil datasets, now under full
experiment tracking — the point is that in engineering practice the *record* of what you
tried and why is a deliverable, not an afterthought. This sets up A5.

**Readings & resources:**
- MLflow documentation: "MLflow Tracking" and "Model Registry" quickstarts.
- Optuna documentation: "Key Features" and the scikit-learn/pruning tutorials.
- Bergstra & Bengio, "Random Search for Hyper-Parameter Optimization," *JMLR* 2012.
- Li et al., "Hyperband: A Novel Bandit-Based Approach to Hyperparameter Optimization,"
  *JMLR* 2018.

## Teaching notes / common pitfalls
- Students routinely report the *best validation* score as if it were test performance.
  Hammer the "test set touched once" rule and make them write the final number from a
  locked test split.
- The Combined Cycle Power Plant rows are close to i.i.d., so plain k-fold is fine — use it
  as the contrast case, then show a dataset (turbofan, bearings in Wk6) where GroupKFold or
  TimeSeriesSplit is mandatory. Make the choice a graded justification, not a default.
- Many will fit the scaler before splitting. Force the use of a scikit-learn `Pipeline` so
  preprocessing is inside CV; this single habit prevents most leakage.
- MLflow's local file store is enough; don't let students burn time standing up a tracking
  server. Do insist they log the dataset hash and git SHA — "reproducible" means someone
  else can regenerate the number.
- Optuna can overfit the validation set if the budget is huge. Cap trials, keep a locked
  test set, and discuss the 1-SE rule so "biggest model wins" doesn't become the reflex.
