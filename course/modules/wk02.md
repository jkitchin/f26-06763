# Week 02 — Data Acquisition & Storage
**Arc:** Data Systems · **Lectures:** L3–L4

**Prerequisites (from prior weeks):** A `uv`-managed project and git workflow (Wk1). Ability to run a Python script via `uv run`. Basic understanding of tabular data and time-indexed records.

## Module learning objectives
- Design a normalized relational schema for engineering time-series (sensor, unit, reading) and justify keys, types, and indexes.
- Write SQL to load, filter, aggregate, and window sensor data in PostgreSQL, including time-bucketed aggregates.
- Explain the row-store vs. column-store trade-off and when Parquet/columnar beats a relational database.
- Query Parquet files directly with DuckDB and move data between PostgreSQL, DuckDB, and Parquet.
- Describe document/NoSQL and vector stores and where each fits an engineering data platform.

## Lecture L3 — Relational databases and SQL for engineering time-series
**Objectives:**
- Model sensor/simulation data in a relational schema with appropriate types (timestamps, numeric precision, units).
- Load data into PostgreSQL and query it with SQL: joins, `GROUP BY`, window functions, time bucketing.
- Reason about indexing and query cost for time-range queries.

**Topics:**
- Relational model refresher: tables, primary/foreign keys, normalization, and why a `readings(sensor_id, ts, value)` long format usually beats a wide "one column per sensor" table.
- PostgreSQL types that matter for engineering: `timestamptz`, `numeric` vs `double precision`, `interval`; storing units and calibration metadata.
- SQL essentials: `SELECT/WHERE/JOIN/GROUP BY/HAVING`, aggregates, `DISTINCT`, `CASE`; window functions (`LAG`, `AVG OVER`) for rolling computations; date_trunc for time buckets.
- Loading data: `COPY`, `psql`, and from Python via `psycopg`/SQLAlchemy.
- Indexing basics: B-tree on `(sensor_id, ts)`, when an index helps a range scan, `EXPLAIN ANALYZE`. Brief mention of TimescaleDB hypertables as a domain extension.

**Live demo / in-class activity:** Spin up PostgreSQL in Docker, create a `sensors`/`readings` schema, `COPY` the Intel Berkeley Lab sensor data in, and answer engineering questions live: average temperature per sensor per hour, sensors with anomalous voltage, gaps in reporting. Show `EXPLAIN ANALYZE` before and after adding an index.

**Engineering framing / dataset:** Intel Berkeley Research Lab sensor data — 54 Mica2Dot motes logging temperature, humidity, light, and voltage every ~31 s over about a month (~2.3M readings). Realistic messiness: dropouts, dying-battery voltage drift, out-of-range spikes.

**Readings & resources:**
- PostgreSQL documentation, "Tutorial" and "Window Functions."
- "The Data Engineering Cookbook" or Kleppmann, *Designing Data-Intensive Applications*, Ch. 3 (storage & retrieval) — recommended.
- TimescaleDB docs, "Hypertables" (overview only).
- Intel Lab Data dataset page (schema and download).

## Lecture L4 — Document/NoSQL, columnar & Parquet, DuckDB, vector-store preview
**Objectives:**
- Explain columnar storage and why it accelerates analytical scans; read/write Parquet.
- Use DuckDB to query Parquet and PostgreSQL without a server, and choose between OLTP and OLAP tools.
- Place document, key-value, and vector stores in the engineering data landscape.

**Topics:**
- Row vs. column stores; compression and predicate pushdown; when column stores win (wide scans, analytics) and lose (point writes/updates).
- Parquet: schema, types, row groups, partitioning by date/sensor; writing from pandas/PyArrow.
- DuckDB: in-process analytics, querying Parquet/CSV/PostgreSQL directly, `read_parquet`, `COPY ... TO`; DuckDB vs. PostgreSQL vs. pandas.
- NoSQL landscape: document (MongoDB) for heterogeneous experiment metadata, key-value for configs/caches, time-series DBs (InfluxDB) — trade-offs vs. relational.
- Vector stores preview (expanded in the LLM/RAG arc): embeddings as rows, similarity search, why they exist; do not build one yet.

**Live demo / in-class activity:** Convert the Intel Lab `readings` table to partitioned Parquet, then run the *same* analytical query in pandas, PostgreSQL, and DuckDB and compare lines of code and wall-clock time on a laptop. Show DuckDB reading straight from the PostgreSQL instance and from Parquet with zero import step.

**Engineering framing / dataset:** Same Intel Lab dataset, now stored three ways (PostgreSQL, Parquet, DuckDB) to make the storage trade-off concrete. Optional larger-scale comparison with a NYC Taxi Parquet file for column-store scaling intuition.

**Readings & resources:**
- DuckDB documentation, "Querying Parquet Files" and "PostgreSQL extension."
- Apache Parquet documentation, "File Format" overview.
- Kleppmann, *Designing Data-Intensive Applications*, Ch. 3 ("Column-Oriented Storage").
- MongoDB and InfluxDB "Introduction" docs (skim for landscape awareness).

## Teaching notes / common pitfalls
- Students default to wide tables (one column per sensor). Push the long/tidy `(entity, ts, variable, value)` form and discuss the trade-offs explicitly.
- Timezone and timestamp handling is a recurring bug source; insist on `timestamptz` and UTC storage.
- Docker friction eats class time. Provide a ready `docker-compose.yml` for PostgreSQL and a fallback (a hosted free-tier or SQLite for the SQL-only parts).
- Students conflate DuckDB and PostgreSQL. Frame it as OLAP (analytics, embedded) vs. OLTP (transactions, server) rather than "which is better."
- `EXPLAIN ANALYZE` output intimidates people; teach them to read just the top node and total time first.
