# Week 01 — Foundations: The AI-Engineering Stack & Reproducible Work
**Arc:** Foundations · **Lectures:** L1–L2

**Prerequisites (from prior weeks):** None. Assumes basic Python (functions, imports, virtualenv concept), comfort at a terminal, and a GitHub account. Install prerequisites before L1: a working `git`, Python 3.11+, and `uv` (`curl -LsSf https://astral.sh/uv/install.sh | sh`).

## Module learning objectives
- Describe an AI-in-engineering system as a set of stages (data → features → model → evaluation → serving) and locate where failures and iteration actually happen.
- Explain why reproducibility is a first-class engineering requirement (regulated data, safety cases, model audits) and not just good hygiene.
- Create a fully reproducible Python project with `uv`: pinned interpreter, locked dependencies, and a one-command environment rebuild.
- Version code, data, and model artifacts appropriately, and know why large binaries do not belong in plain git.
- Refactor an exploratory notebook into a runnable, importable module with a command-line entry point.
- Set up MLflow tracking and log a first parameterized run.

## Lecture L1 — The AI-Engineering landscape and the modern toolchain
**Objectives:**
- Map the end-to-end lifecycle of an engineering ML system and identify the standardized toolchain used all semester.
- Contrast "a model in a notebook" with "a system": data contracts, drift, monitoring, and the fact that the ML code is, in Sculley et al.'s words, "tiny in proportion to the rest of the system."
- Motivate the course's engineering domains: sensor/IoT time series, simulation outputs, experimental data, surrogate models.

**Topics:**
- The system view: data acquisition → storage → pipelines → features → training → evaluation → deployment → monitoring. Where each later course arc plugs in.
- Why engineering data is different: physical units, calibration/drift, irregular sampling, provenance, safety and regulatory traceability.
- The Sculley et al. "hidden technical debt" framing — glue code, pipeline jungles, undeclared consumers.
- Our standardized stack and the *why* for each choice: Python + `uv` (environments/deps), PyTorch (DL), MLflow (experiment tracking), PostgreSQL/DuckDB/Parquet (storage, Wk2), pandas/Polars (Wk3).
- Local vs. cluster vs. cloud; when a laptop is enough.

**Live demo / in-class activity:** Walk a single notebook that ingests the UCI Air Quality sensor dataset (metal-oxide gas sensors, hourly), plots CO(GT) vs. a sensor response, and shows a naive train/test split. Then show the *same* analysis failing to reproduce on a fresh checkout (missing package version, unpinned random seed, absolute file path). Students diagnose each break.

**Engineering framing / dataset:** UCI Air Quality Data Set (De Vito et al., 2008) — 9,358 hourly instances from a multisensor gas device deployed in an Italian city, with sensor drift over a year. Classic example of a real deployed-sensor dataset with calibration issues.

**Readings & resources:**
- D. Sculley et al., "Hidden Technical Debt in Machine Learning Systems," NeurIPS 2015.
- Google, "Rules of Machine Learning: Best Practices for ML Engineering" (Zinkevich).
- `uv` documentation, "Getting started" (Astral).
- UCI Machine Learning Repository, Air Quality Data Set page (dataset description and citation).

## Lecture L2 — Reproducible environments, version control, and experiment hygiene
**Objectives:**
- Build and lock a project environment with `uv` and rebuild it deterministically.
- Choose the right versioning tool for code vs. data vs. models.
- Convert a notebook into a script/package with a tested entry point and log the run to MLflow.

**Topics:**
- `uv` in practice: `uv init`, `uv add`, `uv.lock`, `uv run`, pinning the Python version with `.python-version`; the difference between a lockfile and `requirements.txt`.
- Project layout that scales: `src/` layout, `pyproject.toml`, `data/` (git-ignored raw, tracked schema), `notebooks/`, `scripts/`, `tests/`.
- Git essentials for ML: `.gitignore` for data/artifacts, meaningful commits, why 200 MB Parquet files break repos; preview of data versioning (DVC/`git-lfs`, expanded Wk4).
- Notebook → script → package: extracting functions, `if __name__ == "__main__"`, argument parsing, deterministic seeds.
- Experiment hygiene: MLflow tracking basics — `mlflow.start_run`, log params/metrics/artifacts; one run = one reproducible fact.

**Live demo / in-class activity:** Live-scaffold a project from empty directory to `uv run python -m airquality.train` in ~15 minutes: `uv init`, add pandas + scikit-learn + mlflow, move notebook cells into `src/airquality/`, add a CLI, run it twice with different seeds, and open the MLflow UI to compare the two runs.

**Engineering framing / dataset:** Same UCI Air Quality dataset carried from L1 so the focus stays on tooling, not domain onboarding.

**Readings & resources:**
- `uv` docs: "Projects" and "Locking and syncing."
- Pro Git (Chacon & Straub), Chs. 1–2 (free online).
- MLflow documentation, "MLflow Tracking Quickstart."
- The Turing Way, "Reproducible Research" chapter.

## Teaching notes / common pitfalls
- The widely repeated "<10% of the code is the model" figure does **not** appear in the Sculley paper, which says only that the ML Code box is "tiny in proportion to the rest of the system." L1 uses the discrepancy deliberately, as a first example of checking a claim against its source. Do not reintroduce the number.
- Many students conflate `uv` with `pip`; emphasize that the lockfile + pinned interpreter is what makes rebuilds deterministic. Have them delete `.venv` and rebuild in class.
- The most common reproducibility break is absolute paths and hidden notebook state (out-of-order cell execution). Force `Restart & Run All` before they trust any notebook.
- Students routinely commit the raw dataset. Set up `.gitignore` early and discuss why (repo bloat, license/PII). Keep only a small schema/sample file tracked.
- MLflow "just works" locally with a file store; do not let students over-configure a server in Week 1. That comes later.
- Windows/macOS/Linux path and shell differences will surface. Standardize on `uv run` for every command so behavior is identical.
