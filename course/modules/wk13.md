**Arc:** Production & responsibility · **Lectures:** L23–L24

## Module learning objectives
- Set up **CI/CD for an ML/LLM system**: automated tests, an eval gate that blocks regressions, and reproducible container builds on push.
- Detect and reason about **drift** (data drift, concept drift, prediction drift) and **regression**, and design monitoring that would catch a real production failure.
- Analyze **cost in production** over time and identify the levers that actually move it.
- Enumerate **failure modes** of LLM/agent and surrogate systems and design concrete **safety guardrails** for each.
- Apply a **responsible-AI lens to engineering decisions**: where an AI recommendation feeds a physical/safety-critical decision, what accountability, human-in-the-loop, and documentation are required.
- Use a **capstone studio/clinic** session to finalize a deployable final-project build — wiring CI, monitoring, and guardrails onto your own system with instructor and peer feedback.

## Lecture L23 — CI/CD for ML, drift & regression monitoring, cost, failure modes & responsible AI
**Objectives:**
- Build a CI pipeline that runs tests and an **eval gate** (fail the build if a key metric drops below threshold) and produces a deployable container.
- Design drift and regression monitoring and choose alert thresholds you can justify.
- Identify system-specific failure modes and write concrete guardrails; apply a responsible-AI checklist to an engineering decision.

**Topics:**
- **CI/CD for ML/LLM systems**: what's different from normal software CI — you test *behavior on data*, not just code. Pipeline stages: lint/unit tests → build container → run the eval harness on the frozen set → **gate on a metric threshold** (e.g., block merge if RAG faithfulness < 0.9 or surrogate MAE regresses > X%) → deploy on pass. GitHub Actions as the concrete tool; MLflow to record each run's metrics for comparison. Nondeterminism: pin seeds, set temperature=0 where possible, or gate on a distribution/tolerance rather than exact match.
- **Drift and monitoring**:
  - *Data/covariate drift*: production inputs move outside the training/eval distribution (new operating regime, new sensor). Detect with distribution distance (PSI, KS test) on input features.
  - *Concept drift*: the input→output relationship changes (equipment ages, catalyst deactivates) — the model is now wrong even on familiar inputs.
  - *Prediction drift*: output distribution shifts even without labels (a proxy when ground truth is delayed).
  - For LLM/agent systems: monitor refusal rate, tool-error rate, judge scores over time, latency/cost, and output-length creep.
  - Thresholds and alerting: static thresholds vs. rolling baselines; the cost of false alarms vs. missed drift.
- **Cost in production**: tracking cost per request and total spend over time; watching for prompt/context bloat, retry storms, and runaway agent loops; setting budgets and rate limits.
- **Failure modes & safety** (the core engineering-responsibility content):
  - LLM/agent: hallucinated facts and citations, confident wrong numbers, prompt injection (especially in RAG/agent tool use), unsafe tool actions (an agent that can write to a system or trigger an actuator), infinite loops, silent schema drift.
  - Surrogate/ML: extrapolation beyond training domain, over-confident uncertainty, stale model, silent input-unit errors.
  - **Guardrails**: input validation and domain checks ("is this operating point inside the model's valid range?"), output validation (schema, numeric bounds, physical plausibility), retrieval grounding + citation-required, tool allow-lists and dry-run/confirmation for actuating tools, human-in-the-loop for high-consequence decisions, rate/loop limits, and fallbacks.
- **Responsible AI for engineering decisions**: engineering AI often feeds decisions with physical, safety, environmental, or economic consequences. Themes: accountability (who signs off), transparency (can you explain *why* the model recommended this), appropriate reliance (calibrated trust, not automation bias), documentation (**model cards / datasheets** for the surrogate; system cards for the agent), validation before a model enters a design or control loop, and knowing when *not* to deploy AI. Standards to be aware of: NIST AI Risk Management Framework.

**Live demo / in-class activity:** Add a GitHub Actions workflow to the Wk12 repo that, on push, installs with `uv`, runs unit tests, runs the eval harness on the frozen set, and **fails the job if the metric is below threshold** — demonstrate by pushing a change that degrades a prompt and watching CI go red. Then, in a notebook, inject a batch of out-of-distribution operating points into the surrogate's input stream and compute a PSI/KS drift score that trips an alert. Close with a 10-minute group exercise: for one deployed system, fill a failure-mode → guardrail table and mark which decisions require a human sign-off.

**Engineering framing / dataset:** Continue the pump/compressor **maintenance agent** and the **process surrogate**. Drift scenario: a compressor is retrofitted (new operating envelope) so live inputs drift out of the surrogate's training domain — monitoring must catch it before the surrogate's bad prediction reaches a design decision. Responsible-AI case: the agent recommends deferring a maintenance action — who is accountable, what documentation and human check are required before that recommendation is acted on?

**Readings & resources:**
- NIST AI Risk Management Framework (AI RMF 1.0), 2023.
- Mitchell et al., "Model Cards for Model Reporting" (FAT* 2019); Gebru et al., "Datasheets for Datasets" (2021).
- Chip Huyen, *Designing Machine Learning Systems* (O'Reilly, 2022) — data distribution shifts, monitoring, and continual learning chapters.
- Greyling / OWASP, "OWASP Top 10 for LLM Applications" — prompt injection and LLM-app risks.
- GitHub Actions documentation — workflows, jobs, and status checks.
- Sculley et al., "Hidden Technical Debt in Machine Learning Systems" (NeurIPS 2015) — why the model is the small part.

## Lecture L24 — Capstone studio: integration, evaluation & deployment clinic
**Format:** A hands-on studio/clinic session — no new lecture content. Students work on their final projects in class while instructor and TAs circulate as a clinic; short structured peer check-ins are built in. This is the week's second "day," dedicated to getting each project *deployable and evaluated* before the Week-14 presentations.

**What to accomplish in the studio (a working checklist):**
1. **Integration:** the LLM/agentic (or surrogate-integrated) system runs end-to-end from a clean `uv` checkout.
2. **Evaluation:** the frozen eval set is in place and the harness produces the metrics you'll report — including at least one honest failure case.
3. **Deployment:** the service is reachable behind FastAPI + Docker with recorded p50/p95 latency and per-request cost.
4. **Guardrails & monitoring:** the failure-mode → guardrail table from L23 is applied to *your* system; a basic drift/observability hook is wired.
5. **CI eval gate** (from L23) runs on push.

**Clinic structure:** ~15-minute rotating slots where each team demos current state to an instructor/TA and one peer team, gets one blocking-issue triage and one concrete next step, and logs it. Teams stuck on the same problem (deployment, eval harness, retrieval quality) are grouped for a targeted mini-huddle.

**Peer check-in:** Each team gives and receives one structured check-in (one strength, one blocking risk, one suggestion). Counts toward participation.

**Deliverable checkpoint:** By end of studio, every team confirms which of the five checklist items are done and names the gap to close before Week 14. Recorded demo and repo are due **before the Week-14 presentation slot** so grading isn't hostage to a live-demo failure. Rubric: see `final-project.md` (100-pt table, 30% of course grade).

## Teaching notes / common pitfalls
- **The eval gate is the point of CI here.** Students default to "run pytest." Push them to make CI fail on a *quality* regression, not just a syntax error — that's the ML-specific skill.
- **Drift without labels is normal.** In engineering, ground-truth labels arrive late or never. Teach input-drift and prediction-drift proxies, not just accuracy-on-new-labels.
- **Guardrails must be concrete and system-specific.** Reject "we'll add safety checks." Make them name the failure and the mechanism (bound, allow-list, human sign-off, retrieval-grounding).
- **Responsible AI is not a slide of platitudes.** Anchor it in *their* system's actual decision and consequence: who is accountable, what's documented, where's the human. Model cards make it concrete.
- **Protect the studio as work time.** The L24 clinic only works if students arrive with a running build; require the pre-studio state (runs end-to-end) so slots go to real blockers, not setup. Send teams that are behind to the grouped mini-huddles.
