## Module learning objectives
- Choose **where a model runs** from how it is called, its latency budget and its cost, and
  package and serve it so that the running artifact is the one you built and tested.
- Measure and reason about **latency, throughput and cost**, and release changes in a way that
  limits the damage a bad one can do.

**Rewritten 2026-11-04** after a research pass. Three corrections to the earlier spec: the
surrogate with uncertainty is L14's scikit-learn ensemble on concrete, not a PyTorch model; the
"maintenance-manual agent" never existed (L18 retrieves over the course's own notes); and there
is no course cloud, so the demo runs on localhost and in Colab without Docker, and a cloud
deploy is described rather than required. This is effectively the last technical lecture, so
it deliberately ties back to the systems the course has already deployed: a database server
(L3), an embedded engine (L4), a broker (L6), a model registry (L10), an in-browser model

**Objectives:**
- Choose where a model runs (an in-process library, a long-running HTTP service, a
  serverless container, a batch job, or the user's browser) from its call pattern, latency
  budget and cost, and name the system already deployed in this course that made the same choice.
- Serve a trained model behind a FastAPI endpoint with typed, range-checked request and
  response schemas that carry the prediction's uncertainty and the model version, with the
  model loaded once at startup and separate liveness and readiness checks.
- Package the service in a reproducible container built from the `uv` lockfile, CPU-only where
  the model allows, with no secrets in any image layer.
- Measure p50 and p95 latency and throughput under load, use Little's law and batching to
  reason about capacity, and estimate the cost per request of a model service and of an LLM call.
- Release a change with a staged rollout, a rollback plan and a check against the deployed
  endpoint, and explain from documented incidents what each of those prevents.

**Topics** (minutes of the 90):
- **Why this matters** (5): Knight Capital, 1 August 2012: new code reached seven of eight
  servers, a repurposed flag woke dead code on the eighth, and Knight lost more than $460
  million in about 45 minutes (SEC order). Then the course's own version: on 2026-08-06 the
  Pages build was green while the site served the previous commit for hours.
- **Where a model runs** (12): the five options, each with one documented property: in-process
  (the caller needs the training versions), a long-running service, serverless with scale to
  zero and cold starts (Lambda: under 1% of invocations, 100 ms to over 1 s; Cloud Run minimum
  instances cost money), batch, and the browser (ONNX Runtime Web, WebGPU). The course has made
  every one of these choices already: PostgreSQL as a server you run (L3) against DuckDB inside
  your process (L4); a broker as a long-lived service (L6); batch stages (L5); the L18 chat and
  the practice game running entirely in the browser, with a 15 to 20 minute first load as the
  cold start. A decision table.
- **The service contract** (15): FastAPI with Pydantic request and response models; range
  constraints that turn L9's extrapolation and L14's out-of-domain inputs into a 422 rather
  than a confident number (L3's "a typed column is still not a validated column"); a response
  that carries the interval and the model version; OpenAPI generated from the types; the
  model loaded once in a `lifespan` handler (`on_event` is deprecated); `def` against
  `async def` and why a CPU-bound `predict` inside `async def` stalls every client; workers
  multiply model memory. Model artifacts: L10's registry; scikit-learn's pickle security and
  version lock (skops, ONNX); `torch.save` of a `state_dict`, `weights_only=True` since
  PyTorch 2.6, TorchScript deprecated in favour of `torch.export` and ONNX (L13 named ONNX).
  Training-serving skew: serve the fitted `Pipeline` (L8), compute features one way (L1, L7,
  Rules of ML #29 and #32), pin the embedding model with the index (L18).
- **Packaging** (15): from L2's "when you need to freeze the entire stack ... the tool is a
  container" to a Dockerfile: uv's guide (pinned uv binary, `uv sync --locked`, dependencies in
  their own layer, cache mount, bytecode, multi-stage, `.dockerignore`), and why the notes use
  it rather than the FastAPI page's `requirements.txt` export; CPU-only torch (about 210 MB
  against more than 1 GB) and base images (43 MB slim against 2 to 14 GB CUDA); non-root;
  exec-form `CMD` so `lifespan` shutdown runs. Secrets: twelve-factor config, `ARG` and `ENV`
  persist in layers and `docker history`, build secret mounts, rotate rather than scrub; the
  course's examples (L3's plaintext demo credentials, the plant stream's mode-640 secret file,
  the game's CI secret). Health checks: L3's `pg_isready`, Docker `HEALTHCHECK`, Kubernetes
  liveness against readiness ("the process is up" is not "the model is loaded").
- **Latency, throughput and capacity** (15): percentiles rather than means (SRE book), and why
  L11 rightly reported minimums for a microbenchmark but a service reports p95; tail at scale
  (one slow server in a hundred makes 63% of fan-out requests slow; hedged requests); Little's
  law as a worked check on NVIDIA's Triton numbers; waiting time as 1/(1−ρ) near saturation;
  batching as the throughput lever (L3's two million statements against `COPY`, L5's
  vectorization, L15's `q=4`, Triton's dynamic batcher and its latency trade-off); for LLMs,
  time to first token, inter-token latency, output length dominating, streaming over SSE,
  continuous batching. The "100 ms costs Amazon 1%" figure traced to a single slide bullet,
  and Google's controlled 2009 result (100 to 400 ms cost 0.2% to 0.6% of searches).
- **Cost** (8): cost per request for a CPU service, for an ensemble (L14: M models cost M
  times), for a GPU, and for an LLM (input and output tokens priced separately, batch and
  prompt-caching discounts, quoted with the date fetched); warm minimum instances against cold
  starts; retries that multiply load (a five-deep stack with three retries each is 243 times),
  backoff with jitter, and why retries need idempotency (L5, L6).
- **Releasing changes safely** (12): a deploy is any change, including configuration, content
  and model weights (CrowdStrike, 19 July 2024: 21 fields expected, 20 supplied, about 8.5
  million machines by Microsoft's estimate); canaries and staged rollouts (SRE workbook);
  verifying every replica runs the new artifact and that a rollback is itself a change
  (Knight); testing what you shipped, which is the job of this site's `build-info.json` check;
  SLIs, SLOs and error budgets; backups you have restored (GitLab, 31 January 2017: `pg_dump`
  9.2 against PostgreSQL 9.6 and failure emails nobody received, the L3 database's failure
  mode); tools that enforce invariants (AWS S3, 2017); a global push channel and a "simulate"
  mode that still ran (Cloudflare, 2019). The course's own small incidents: Debian's mosquitto
  built without WebSockets, nginx's 60 s proxy timeout, D1 without `--remote`.
- **Limitations and trade-offs** (5): when not to build a service at all; what FastAPI is bad
  at (heavy background compute, CPU-bound work under the GIL); when to reach for a dedicated
  inference server (Triton, vLLM); the operational weight of Kubernetes; what serverless
  costs in cold starts; managed platforms against running your own.
- **In-class demo** and recap (3).

**Live demo / in-class activity:** `l21-deployment.ipynb`, runnable in Colab with no Docker and
no cloud account. (1) Fit L14's five-network scikit-learn ensemble on concrete with the
grouped-split recalibration, and save it with a manifest (versions, data hash, SHA-256 of the
artifact). (2) Write `app.py`: `POST /predict` and `POST /predict_batch` with range-checked
Pydantic models, a response carrying the mean, the interval, an out-of-domain flag and the
model version, `/healthz` (liveness) and `/readyz` (readiness), the model loaded in `lifespan`.
(3) Exercise it in-process with `TestClient`, including a 422 for an out-of-range mix. (4) Start
it with `uvicorn` as a background process on localhost and load it with `httpx`: p50, p95 and
throughput at several concurrencies, a Little's-law check, one request at a time against one
batch, and the same handler written as `async def` to show the stall. (5) Point a short L15-style
optimization loop at the endpoint and count its calls. (6) Cost per thousand requests from a
dated price, and the token cost of the same answer from an LLM. (7) A generated Dockerfile; the
build, `docker history` and secret-mount cells run only where Docker exists and say so
otherwise.

## Teaching notes / common pitfalls
- **Load the model once.** The most common deployment bug is loading weights/index inside the request handler → seconds of latency per call. Use FastAPI lifespan/startup.
- **Secrets in images / keys in git.** Watch for API keys committed or baked into Docker layers. Environment variables and secret managers only.
- **Test the thing you shipped.** Checking only the local Python function, never the deployed HTTP endpoint, hides serialization, timeout, and concurrency bugs. Point the check at the URL.
- **`async def` is not a speed-up.** A CPU-bound `predict` inside `async def` blocks the event loop for every client; plain `def` runs in a threadpool. Students reach for `async` because it sounds faster. Show the stall in the demo rather than asserting it.
- **Workers multiply memory.** Four workers hold four copies of the model (FastAPI's deployment-concepts page). Size the container for that, or run one process per container and replicate outside it.
- **The default Linux `torch` is the CUDA build.** `uv add torch` on Linux pulls well over a gigabyte of CUDA libraries for a model that runs on CPU. Configure the CPU index (uv's PyTorch guide) before writing the Dockerfile.
- **Means hide the tail.** Students report mean latency because L11 reported minimums. A service is judged on p95 and p99; insist on percentiles and the concurrency they were measured at.
- **The folklore numbers.** "Every 100 ms costs 1% of sales" will come up. It is one slide bullet with no method; Google's controlled 2009 experiment is the citable number. Same move as L1's "less than 10% is ML code".
- **Cross-references to unreleased lectures.** L19 and L20 are unreleased at the time of writing. Link them from the notes only if they are released before L21 (CLAUDE.md section 9 step 0); otherwise name them in prose.
