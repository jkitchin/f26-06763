# Assignment 8 — Structured extraction from engineering documents
**Module:** Week 09 · **Released:** L15 · **Due:** ~1 week later · Part of the 45% assignment pool.

## Goal
Build and **evaluate** an LLM-powered extractor that turns messy, unstructured engineering text (datasheets, specs, or inspection/maintenance reports) into a **schema-validated, normalized table**. You will call a hosted LLM API, enforce a structured-output schema, validate every record, account for token cost, and measure extraction accuracy against a gold set — with a documented prompt-improvement iteration.

This is a systems/engineering task: using the LLM is expected and easy; the graded work is designing the schema, the validation/repair loop, the evaluation, and the cost/reliability engineering around the model.

## Learning outcomes assessed
- Call a hosted LLM API and manage the prompt/message interface, `max_tokens`, temperature, and token-usage accounting.
- Produce and validate schema-constrained structured output; handle missing/invalid fields without hallucination.
- Design a prompt methodically and measure its quality on a labeled gold set rather than by inspection.
- Normalize engineering values (units, numeric types, ranges) reliably.
- Engineer for reliability: retries, logging, no silent truncation, reproducibility.

## Corpus / dataset
Choose **one** engineering document type (10–20 documents), provided by the instructor or self-sourced with approval:
- Component datasheets (valves, pumps, fasteners, sensors, electronic parts), **or**
- Material specifications / mill certificates, **or**
- Free-text maintenance/inspection/failure reports.

Requirements for the set:
- At least **2–3 documents must be incomplete or malformed** (a missing field, a scanned/garbled section, conflicting values) to exercise the "not found" and validation paths.
- You must hand-label a **gold set of ≥ 15 documents** with the correct field values (this is your evaluation ground truth). Keep it in a separate file from any prompt examples.

## Tasks (numbered, concrete, buildable in a week)
1. **Define the target schema** as a Pydantic model (or JSON Schema) with at least 6 fields, including at least two numeric fields with explicit **units**, one categorical/enum field, and one optional field that is legitimately absent in some documents. Document each field's meaning and expected type/units.
2. **Token & cost baseline:** For each document, count input tokens with the provider's tokenizer/counting endpoint. Report the token distribution and flag any document that approaches the model's context limit; handle it explicitly (do not silently truncate).
3. **Build the extractor:** Send each document to the LLM using **schema-enforced structured output** (provider JSON-schema/structured-output mode *or* a typed tool/function call). Use low temperature. Parse and **validate** each response against your schema.
4. **Validation & repair loop:** On validation failure or a missing required field, implement a bounded repair strategy (e.g. one re-ask with the validation error, or a fallback to null with a logged reason). The pipeline must never crash on a bad document and must never invent a value that isn't in the source.
5. **Normalization:** Convert extracted values to canonical units/types (e.g. all pressures → MPa, all masses → kg, ranges → `(min, max)`). Record original + normalized.
6. **Evaluation:** On your ≥ 15-document gold set, compute **field-level accuracy** (per field and overall) and a **document-level exact-match** rate. Report where extraction fails and why (units, missing fields, hallucination, parse error).
7. **Prompt iteration:** Produce **two** prompt versions (a naive baseline and an improved one). Report the accuracy *and* cost delta between them on the gold set, and explain what changed and why.
8. **Reliability:** Add retry-with-backoff on rate-limit/5xx errors and log, per call, the prompt, response, token usage, and estimated cost to a file (or MLflow).
9. **Reproducibility:** Ship a `uv`-managed project that runs end to end with one command, reads the model ID and API key from config/env (no hard-coded secrets), and pins the exact model ID used.

## Deliverables
- A `uv` project (repo or archive): extractor code, schema definition, gold-set file, and the run/eval scripts.
- The output **normalized table** (CSV/Parquet) for the full corpus.
- A **per-call usage log** (prompt/response/tokens/cost).
- A **report (2–4 pages)** covering: schema design and rationale; token/cost analysis; the two prompt versions and their gold-set accuracy + cost; the field-level and document-level metrics; a failure analysis; and the exact provider/model ID used.
- A `README` with the one-command run instructions.

## Allowed tools & AI-use note
Using an LLM API **is the assignment** — that is expected and required. "Your own work" here means: **you** design the schema, the validation/repair logic, the normalization, the gold set, the evaluation, and the prompt-iteration analysis; and **you** write the report and can explain every design choice. You may use any hosted provider (Anthropic, OpenAI, or another) and any embedding/tokenizer utilities. You may use an AI coding assistant to help write glue code, but the extraction pipeline, the evaluation, and the analysis must be yours and understood by you — be prepared to explain your code and results in a short check-in. Do **not** hand-label your gold set with the same model you're evaluating (no self-grading). Cite the exact model ID and any libraries used.
