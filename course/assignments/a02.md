# Assignment 2 — Sensor Data into PostgreSQL + DuckDB
**Module:** Week 02 · **Released:** L3 · **Due:** ~1 week later · Part of the 45% assignment pool.

## Goal
Design a relational schema for a real multi-sensor time-series dataset, load it into PostgreSQL, and answer a set of engineering questions with SQL. Then store the same data as partitioned Parquet and query it with DuckDB, comparing effort and performance. You will experience firsthand the OLTP vs. OLAP / row-store vs. column-store trade-off.

## Learning outcomes assessed
- Model engineering time-series in a normalized relational schema with correct types.
- Write non-trivial SQL: joins, aggregates, window functions, time bucketing.
- Reason about indexing with `EXPLAIN ANALYZE`.
- Convert data to Parquet and query it with DuckDB.
- Articulate when a column store or embedded engine is the right tool.

## Dataset
Intel Berkeley Research Lab sensor data — 54 motes logging temperature, humidity, light, and voltage roughly every 31 s for about a month (~2.3M readings), plus a mote location/connectivity file. Download the `data.txt` and `mote_locs.txt` from the Intel Lab Data page.
**Fallback:** UCI "Individual Household Electric Power Consumption" (2M+ minute-level readings) or the Wk1 Air Quality data if Intel Lab is unavailable; document your choice and adapt the schema.

## Tasks
1. Bring up PostgreSQL (provided `docker-compose.yml`, or a free hosted instance). Design a normalized schema — at minimum a `sensors` dimension and a long-format `readings(sensor_id, ts, variable, value)` (or a typed `readings` table) with a foreign key and correct types (`timestamptz`, numeric).
2. Load the data via `COPY` or a Python loader (`psycopg`/SQLAlchemy). Handle malformed rows, bad timestamps, and dying-battery voltage anomalies (document your cleaning rules).
3. Write SQL answering at least these: (a) hourly average temperature per sensor via `date_trunc`; (b) the 5 sensors with the most missing/dropped intervals; (c) a rolling 1-hour average voltage per sensor using a window function; (d) detect readings outside a plausible physical range.
4. Add an index supporting time-range-per-sensor queries; show `EXPLAIN ANALYZE` before and after and report the difference.
5. Export the readings to date-partitioned Parquet (pandas/PyArrow), then reproduce query (a) and (c) in DuckDB directly against the Parquet files.
6. Run one analytical query in pandas, PostgreSQL, and DuckDB; record lines of code and wall-clock time for each.

## Deliverables
- Repo with `schema.sql`, load script, a `queries.sql` (or notebook) with all SQL and results, and the Parquet export/DuckDB script.
- A short REPORT.md (≤1 page): schema diagram/description, indexing before/after, the three-way comparison table, and 2–3 sentences on when you would choose each store.
- `docker-compose.yml` or connection instructions; raw data not committed.
