# Assignment 9 — RAG system over an engineering corpus
**Module:** Week 10 · **Released:** L17 · **Due:** ~1 week later · Part of the 45% assignment pool.

## Goal
Build a **retrieval-augmented QA system** over an engineering corpus and **rigorously evaluate** it — separating retrieval quality from answer quality. You will chunk and index a corpus, retrieve and ground generations with source citations, and measure retrieval metrics (recall@k etc.) and answer metrics (correct, grounded/faithful, cited) against a gold set. You will then run a **controlled comparison** of at least two design variants and justify your final configuration with numbers.

The engineering/system-building is graded, not the fact that an LLM produces fluent text. Grounding and honest evaluation are the point.

## Learning outcomes assessed
- Build each stage of a RAG pipeline: chunk → embed → index → retrieve → ground → generate with citations.
- Choose chunking, embedding, and retrieval parameters deliberately and justify them with retrieval-quality metrics.
- Measure retrieval quality (recall@k, precision@k, MRR or nDCG) and answer quality (correctness, groundedness/faithfulness, citation validity) on a gold set.
- Diagnose and mitigate RAG failure modes (retrieval miss, stale/duplicate chunks, ungrounded/hallucinated answers).
- Run a controlled comparison and make an evidence-based design decision.

## Corpus / dataset
An engineering document corpus (instructor-provided or self-sourced with approval), large enough that retrieval matters (**≥ 50 pages / ~150+ chunks**). Suitable options:
- Engineering standards/code excerpts, equipment O&M manuals, or design handbooks, **or**
- A set of technical reports / simulation logs / test procedures, **or**
- API/tooling documentation for an engineering software package.

You must build a **gold evaluation set of ≥ 20 questions**, each with:
- the correct answer (short, checkable), **and**
- the ID(s) of the chunk(s) that actually contain the answer (relevance labels for retrieval scoring), **and**
- at least **3 questions whose answer is deliberately *not* in the corpus** (to test refusal/"not found").

## Tasks (numbered, concrete, buildable in a week)
1. **Ingest & chunk:** Load and clean the corpus. Implement chunking with retained metadata (source, section/heading, page, revision). Justify your chunk size and overlap.
2. **Embed & index:** Embed chunks and build a vector index (FAISS, Chroma, Qdrant, or pgvector — your choice). **Pin the embedding model** and use the same model for query and index.
3. **Retrieve:** Implement top-k retrieval with metadata filtering available. Optionally add keyword/hybrid or a re-ranker (encouraged, not required).
4. **Ground & generate:** Assemble a grounded prompt from retrieved chunks; instruct the model to answer **only** from context, **cite chunk/source IDs**, and say "not in the provided documents" when appropriate. Use low temperature.
5. **Retrieval evaluation:** On the gold set, compute **recall@k and precision@k** (for at least two values of k) and **MRR or nDCG**, using your chunk-level relevance labels.
6. **Answer evaluation:** Score **correctness** (against gold answers), **groundedness/faithfulness** (is every claim supported by a retrieved chunk?), and **citation validity** (do the cited chunks actually contain the answer?). Report how "not found" questions are handled. You may use a rubric with manual scoring and/or an LLM-as-judge — if you use a judge, spot-check ≥ 5 of its scores by hand and report agreement.
7. **Controlled comparison:** Vary **one** meaningful design choice (e.g. chunk size, k, embedding model, or with/without re-ranking) across **≥ 2 configurations** and report how retrieval *and* answer metrics change. State your final chosen configuration and why.
8. **Failure analysis:** Show at least one **retrieval-miss → wrong-answer** case and one case your system handles well, and discuss mitigations.
9. **Reproducibility & cost:** `uv`-managed, one-command build/index/eval; log token usage and estimated cost per query; no hard-coded secrets; pin model IDs.

## Deliverables
- A `uv` project: ingestion/chunking, indexing, retrieval, generation, and evaluation code; the gold-set file (questions + answers + relevance labels).
- A **results table** with retrieval metrics and answer metrics for each configuration compared.
- A **report (3–5 pages)**: corpus + chunking rationale; index/embedding choices; the metrics for each variant; the controlled-comparison result and final decision; failure analysis; and the exact embedding + LLM model IDs.
- A short **transcript sample** (3–5 questions) showing grounded, cited answers including one "not found."
- A `README` with one-command run instructions.

## Allowed tools & AI-use note
Building a RAG system with a hosted LLM and an embedding model **is the assignment** — that use is expected. "Your own work" means **you** design the chunking, indexing, retrieval, grounding, and — most importantly — the **evaluation and gold set**, and **you** write the analysis and can defend every metric and design choice. Any provider (Anthropic, OpenAI, others) and any vector DB / retrieval library are allowed; using a framework (LangChain, LlamaIndex) is allowed **but you must be able to explain what each stage does** and your evaluation must be your own, not a framework's opaque built-in. If you use an LLM-as-judge, you must hand-verify a sample. Do not use the same corpus's answer key to auto-generate your gold questions without hand-checking them. Cite all model IDs, the vector DB, and any frameworks. Be ready to explain your pipeline and results in a short check-in.

## Stretch (optional)
- Add hybrid (dense + BM25) retrieval or a cross-encoder re-ranker and quantify the retrieval-metric improvement.
- Add revision-aware filtering (answer only from the current spec revision) and show a query where it changes the answer.
- Compare RAG against a **long-context** baseline (stuff the whole corpus/section into the prompt) on accuracy, cost, and latency, and discuss when each wins — this directly previews the Wk10 L18 prompting-vs-RAG-vs-fine-tuning framework.
