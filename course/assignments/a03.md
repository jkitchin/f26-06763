# Assignment 3 — Reproducible, Validated Data Pipeline
**Module:** Week 03 · **Released:** L6 · **Due:** ~1 week later · Part of the 45% assignment pool.

## Goal
Build a reproducible, multi-stage batch pipeline that ingests a dirty industrial sensor dataset, cleans and transforms it, and enforces data-quality expectations that fail loudly on bad input. You will structure the pipeline as small, testable stages and prove your validation actually catches corruption.

## Learning outcomes assessed
- Decompose a pipeline into pure, parameterized, reproducible stages.
- Use pandas and/or Polars idiomatically for cleaning and transformation.
- Encode schema, range, and physical-plausibility checks with pandera and/or Great Expectations.
- Make a pipeline fail (or quarantine) on invalid data and demonstrate it.
- Cache intermediate outputs deterministically (Parquet).

## Dataset
[Tennessee Eastman process simulation data](https://doi.org/10.7910/DVN/6C3JR1) (Rieth et al. 2017, Harvard Dataverse, CC0), the same data from Lecture 5: a simulated chemical plant logging 52 process variables (41 measured, 11 manipulated) every 3 minutes, fault-free operation plus 20 fault types. The `Faulty_Training` file is what you want; reuse or adapt the loader in [`l05-pipelines.ipynb`](../../lectures/l05/l05-pipelines.ipynb) to fetch and cache it.

The raw data is clean by construction: no missing values, no dead channels. Your `ingest` stage must inject realistic defects on purpose, the same class the Lecture 5 demo used (a heavily-dropped-out sensor, a lightly-dropped-out sensor, a channel stuck at a constant), clearly documented as synthetic rather than presented as if the data arrived this way. That gives your `clean` stage real work: something to drop, something to impute.
**Fallback:** The Intel Lab sensor data (Wk2) or UCI Air Quality, both naturally dirty already; if you switch, define equivalent quality checks appropriate to that data. Document your choice.

## Tasks
1. Build a pipeline of ≥4 explicit stages, each a pure function with typed input/output: `ingest` → `clean` (drop constant & high-missing columns, impute — using training statistics only) → `transform`/`featurize` → `persist`. Cache each stage's output to Parquet; make re-runs idempotent.
2. Provide a single reproducible entry point (`uv run python -m pipeline.run --config config.yaml`) that runs the full pipeline from raw to processed. Parameterize thresholds (e.g., missingness cutoff) via config.
3. Author a validation layer with pandera (a `DataFrameSchema`) and/or Great Expectations covering: column dtypes, value ranges, allowed null fractions, a uniqueness/monotonicity check on the run/timestamp key, and at least one physical-plausibility or domain check. Run validation as a gate before the transform stage.
4. Demonstrate failure: inject corrupted rows (out-of-range values, wrong dtype, broken key ordering) in a test and show the pipeline halts or quarantines them with a clear error/report.
5. Write `pytest` tests for at least two stages and for the validation behavior.
6. Log the run to MLflow: config parameters, row counts in/out per stage, and the validation report as an artifact.

## Deliverables
- Repo with a `pipeline/` package (one module per stage), `config.yaml`, validation schema/suite, `tests/`, and README.
- README (≤1 page): pipeline DAG description, what each check enforces and why, and how to reproduce.
- Evidence (log/screenshot) of the pipeline halting on injected bad data, and the MLflow run.
- Raw data not committed; processed Parquet may be regenerated by the pipeline.
