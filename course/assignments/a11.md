# Assignment 11 — Eval harness + deployed API
**Module:** Week 12 · **Released:** L21 · **Due:** ~1 week later · Part of the 45% assignment pool. (Lighter; can fold into the final project.)

## Goal
Take **one** system you have already built — your Wk10 RAG assistant, your Wk11 agent, or your Wk7 process surrogate — and give it the two things a hobby project lacks and a production system requires: (1) a **versioned evaluation harness** that produces defensible, reproducible metrics, and (2) a **deployment** behind a FastAPI + Docker service on the cloud. Then close the loop by running the harness **against the live endpoint**.

You are not building a new model. You are proving you can *measure* and *ship* one.

## Learning outcomes assessed
- Construct a frozen, versioned evaluation set and a deterministic scoring harness; log results to MLflow.
- Choose valid metrics for your system type (ML metrics with error bars, or LLM/agent metrics including LLM-as-judge), and **validate the judge** against human labels if you use one.
- Instrument requests with tracing: capture inputs, outputs, tool calls, token counts, latency, and cost.
- Wrap the system in a FastAPI service with typed schemas and a health check, containerize it with Docker (uv-based), and deploy to the cloud.
- Measure and report latency (p50/p95) and cost per request, and run the eval harness against the deployed endpoint.

## Dataset / system under test
Pick **one** track (use your own prior work):
- **RAG track** — your Wk10 assistant over the provided equipment-manual / maintenance corpus. Provided `eval_set.jsonl` of {question, reference_answer, must_cite_doc}; you may add 10+ of your own questions.
- **Agent track** — your Wk11 tool-using agent. Provide/curate an eval set of {task, expected_tool_sequence_or_answer, success_check}.
- **Surrogate track** — your Wk7 surrogate. Use a held-out test set (provided per-module) with a designated extrapolation slice.

Whatever you pick, the **eval set must be committed to the repo and versioned** (a hash or version string recorded with each run).

## Tasks (build an eval harness AND deploy behind an API)
1. **Freeze an eval set.** Commit `eval/eval_set.jsonl` (or equivalent). Record its version/hash. Keep it disjoint from any few-shot/prompt examples.
2. **Build the eval harness** (`eval/run_eval.py`): load the set, run the system on each item, capture a per-item **trace** (inputs, outputs, tool calls/retrieved chunks, tokens in/out, latency, model+version), score each item, and aggregate.
3. **Metrics for your track:**
   - RAG/Agent: at least one **programmatic** check (schema validity, retrieval faithfulness, tool-call correctness, or numeric-tolerance match) **and** one **LLM-as-judge** score with a written rubric.
   - Surrogate: MAE/RMSE overall **and per-slice** (interpolation vs. extrapolation), a parity plot, and a bootstrap 95% CI on the headline metric; plus a calibration check if you output uncertainty.
4. **Validate your judge (RAG/Agent only).** Hand-label ≥15 items, report judge–human agreement (% agreement or Cohen's kappa), and comment on where they disagree. If agreement is poor, say so and lean on your programmatic metric.
5. **Log to MLflow.** Aggregate metrics + eval-set version + key params as one run; attach the parity plot / score-distribution plot and the per-item results file as artifacts.
6. **Deploy the system** behind FastAPI: a typed endpoint (`POST /predict` or `/answer` with a Pydantic request/response model reusing your Wk9 schemas), a `/healthz` endpoint, model/index loaded once at startup, and secrets via environment variables.
7. **Containerize with Docker** using `uv` for installs; `.dockerignore`; build and run locally, then **deploy to the course cloud** (GPU only if the model needs it).
8. **Measure latency & cost.** Send a small load (e.g., 50–200 requests) at the live endpoint; report **p50/p95 latency**, throughput, and **cost per request** (token-based for LLMs, GPU-time for self-hosted).
9. **Run the harness against the deployed endpoint** (not just the local function) and confirm the numbers match; note any discrepancies (serialization, timeouts, concurrency).

## Deliverables
- A **repo** (uv-managed, runs from a clean clone) containing: the versioned eval set, `run_eval.py`, the FastAPI app, the `Dockerfile`, and a `README` with exact run/deploy commands.
- The **live endpoint URL** (or a short recording of it responding if the deployment must be torn down for cost).
- An **MLflow run** (screenshot or exported metrics) with the logged metrics and artifacts.
- A **1–2 page report**: what you evaluated, metrics + CI/agreement results, an honest failure case, the deployment (latency p50/p95, cost/request), and the local-vs-deployed comparison.

## Rubric (100 pts)

| Criterion | Pts | What we look for |

| Harness correctness & reproducibility | 15 | Runs from clean clone; deterministic scoring; per-item traces captured |
| Metric validity (right metrics for the track) | 15 | Programmatic + judge (RAG/agent) or per-slice + CI (surrogate); not a single vanity number |

| Docker + cloud deploy | 10 | uv-based reproducible build; runs on cloud; reachable endpoint |
| Latency & cost reporting | 8 | p50/p95, throughput, cost/request measured on the live endpoint |
| Harness-vs-deployment loop + report | 7 | Harness run against live URL; honest report incl. a failure case |

## Allowed tools & AI-use note
Use the standardized toolchain (Python + uv, PyTorch, MLflow, FastAPI, Docker, cloud). Any LLM/agent framework or provider is fine. You may use AI coding assistants — but **you must be able to explain every line, especially the eval scoring and the deployment config**, and you must run and verify everything yourself. Cite any nontrivial code you adapted. The point of the eval half is honesty: report real numbers and real failures, not the best cherry-picked run.
