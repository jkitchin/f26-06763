# Assignment 4 — Feature Pipeline + Dataset Versioning
**Module:** Week 04 · **Released:** L7 · **Due:** ~1 week later · Part of the 45% assignment pool.

## Goal
Build a leakage-safe feature pipeline for run-to-failure sensor data, design a correct grouped/temporal split, and version both the raw and engineered datasets with DVC so any result reproduces from a commit. You will then quantify the cost of data leakage by comparing a leaky and a correct setup head-to-head.

## Learning outcomes assessed
- Engineer time-series features (lags, rolling statistics, deltas) for physical signals.
- Apply scaling/transforms fit on training data only, inside a leakage-safe pipeline.
- Design and justify grouped (per-unit) and temporal splits.
- Version datasets and feature artifacts with DVC and link them to code + MLflow runs.
- Empirically demonstrate leakage and its inflated metrics.

## Dataset
NASA C-MAPSS Turbofan Engine Degradation Simulation (use FD001 at minimum; more subsets for stretch) — run-to-failure multivariate sensor trajectories for a fleet of simulated engines, a standard Remaining-Useful-Life (RUL) benchmark. Download the C-MAPSS data from the NASA Prognostics Center of Excellence data repository (train/test/RUL text files).
**Fallback:** Any run-to-failure or per-unit time-series (e.g., a bearing-degradation set); if you switch, preserve the per-unit grouping so the split/leakage lessons still apply. Document your choice.

## Tasks
1. Engineer features per engine unit: rolling mean/std of key sensors, deltas from cycle 1, rate-of-change, and time-since-start. Resample/align as needed. Compute the RUL target per cycle.
2. Build the feature transform as a leakage-safe pipeline (e.g., scikit-learn `Pipeline`/`ColumnTransformer`) so scaling/imputation is fit on training units only. Persist the fitted transformer as an artifact.
3. Implement a correct split: group/unit-based (no engine appears in both train and test) and respect temporal order; contrast with `GroupKFold`/`TimeSeriesSplit`. Justify your choice.
4. Demonstrate leakage quantitatively: build a deliberately leaky variant (e.g., scaler fit over all data, or a random row-level split) and compare its RUL metric (RMSE) against the correct pipeline using the *same* simple model. Report and explain the gap.
5. Version data with DVC: track the raw C-MAPSS files and the engineered feature dataset; define a `dvc.yaml` stage that regenerates features from raw. Use a local DVC remote (a directory). Show that `dvc repro` + a clean checkout reproduces the exact feature file.
6. Log both runs (leaky vs. correct) to MLflow, tagged with the DVC data version/hash and the git commit.

## Deliverables
- Repo with a `features/` package, `dvc.yaml`/`.dvc` files, the split logic, saved fitted transformer, `tests/`, and README.
- README (≤1 page): feature list + rationale, split design, the leaky-vs-correct comparison table with the metric gap, and reproduce steps (`dvc pull`/`dvc repro`).
- MLflow comparison of the two runs with data-version tags.
- Raw data tracked by DVC, not committed to git directly.
